### 1d. API token scopes (preview vs production)  ** CONTRADICTS "narrow scope" ASSUMPTION **
Findings: **No token permission separates uploading a preview/version from deploying to production.** From the official OpenAPI (`cloudflare/api-schemas`, field `x-api-token-group`):

- `POST /accounts/{id}/workers/scripts/{script}/deployments` (create deployment = go live) -> `['Workers Scripts Write']`
- `PUT /accounts/{id}/workers/scripts/{script}` (direct upload/deploy) -> `['Workers Scripts Write']`; `DELETE` script -> same.
- Previews API (`/workers/workers/{worker_id}/previews`): list/get -> Read/Write/Tail; update/delete -> Workers Scripts Write; the `create` and `deployments.create` operations show `x-api-token-group` = None (not declared) -> required scope for creating a preview is **UNVERIFIED** from the schema. Docs example says "The API token needs permission to edit Workers Scripts and the resources used by the Preview" (`workers/previews/examples.mdx`).
- Workers Builds previews use a different group: `Workers CI Write/Read` (`/builds/workers/{script_tag}/previews`).
- Pages: `POST /pages/projects/{name}/deployments` -> `['Pages Write']` for both preview and production deployments; production vs preview is decided by `--branch`/`production_branch`, not by scope.
- Docs list only generic items: "Workers Scripts Read/Edit", "Cloudflare Pages Read/Edit", "D1 Read/Edit", "Workers CI Read/Edit" (`fundamentals/api/reference/permissions.mdx`). Resource scoping documented in `create-token.mdx` is by account/zone; per-Worker (script-level) scoping is not documented in anything read (**UNVERIFIED** that it is impossible, but no evidence it exists).

### 4a. What `wails3 package` produces

### 4b. Code signing and SmartScreen [MSLEARN]
- "EV certificates no longer bypass SmartScreen... Paying a premium for EV solely to avoid SmartScreen warnings is no longer justified." (learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation).
- Artifact Signing (formerly Trusted Signing): "~$9.99/month", no hardware token, "Azure Artifact Signing does **not** provide instant SmartScreen trust... typically several weeks and hundreds of clean installs" (MSIX signing guide). Reputation "tied to your verified identity". SignTool needs the Artifact Signing Client Tools (`winget install -e --id Microsoft.Azure.ArtifactSigningClientTools`) with dlib + `metadata.json`; plain SignTool does not work. Certs are short-lived (about 3 days, new daily).
- Eligibility - **Microsoft pages conflict**: code-signing-options and MSIX guide: organizations in USA, Canada, EU, UK; individuals USA and Canada only. Quickstart: orgs also Australia, NZ, Japan, South Korea, Singapore, Switzerland, Norway, Israel. MSIX overview adds "Organizations must have a verifiable tax history of three or more years." Q&A answers (April 2025) mention a 3-year history; **UNVERIFIED** which is current for a brand-new company - re-check at account creation.
- Microsoft Store (MSIX): "No warning - covered by Microsoft's certificate"; Store re-signs the package for free. Unsigned/self-signed = SmartScreen warning ("Windows protected your PC"); Windows 11 Smart App Control "will block execution of unsigned files unless the file has a positive reputation". Reputation applies to publisher identity + file hash; signing every release with the same identity lets later releases inherit; no manual submission path for consumer reputation.
- OV $150-300/yr, EV $400+/yr (Microsoft's table).
### 4c. Updaters
- **Wails v3 has a built-in updater** (`v3/pkg/updater`, tag beta.28): `app.Updater`, `Config{CurrentVersion, Providers, PublicKey, CheckInterval, ...}`, providers (GitHub Releases provider in `providers/github`, token optional: "for public repos it just raises the rate limit from 60 to 5000 req/hour"), SHA digest check, optional Ed25519/Ed25519ph signature verified against a PUBLIC KEY PINNED in app config (`verify.go`; `signatureAlgo` "ed25519", "ed25519ph", "ecdsa-p256"), download -> verify -> unzip -> **spawn detached helper that waits for the PID to exit then renames the new exe over the old** (`updater.go Restart`, `helper_windows.go renameOrCopy`). CLI: `wails3 updater genkey|sign|manifest|verify` ("Wails Update Manifest protocol"). Compatibility: swapping the exe in place works for a user-writable install dir; field report [SEARCH] that NSIS machine-wide install under Program Files breaks self-update (helper not elevated) and that a stale `DisplayVersion` remains - so use `INSTALL_SCOPE=user` (or per-user location) with this updater. MSIX packages are read-only ("Writes inside the package: Not allowed" - MS Learn), so the Wails swap updater cannot apply; MSIX updates go through App Installer / Store.

## 8. Windows-specific facts
- Wrangler: supported OS "macOS 13.5+, Windows 11, and Linux distros that support glib 2.35"; Node >=22; workerd ships a `windows-64` binary (npm optional dep). WSL distro = Linux (glibc >=2.35 needed: Ubuntu 22.04+). Running Wrangler in WSL vs native: no doc statements about WSL file-system performance or localhost forwarding were found (**UNVERIFIED**). Local state lives in `<project>/.wrangler/state` - on a Windows drive accessed from WSL (`/mnt/c`) or the reverse (`\\wsl$`) there is no documented support; prefer keeping worktrees in one OS only.
- Playwright: Windows 11+/Server 2019+/WSL supported; browsers in `%USERPROFILE%\AppData\Local\ms-playwright`; `playwright install-deps` is Linux-only OS-package install (needed in WSL, not on native Windows); download hosts must be reachable.

- Wails: MSIX/NSIS tooling needs Windows (MakeAppx/signtool/makensis); native build with `CGO_ENABLED=0`; WebView2 runtime required (bootstrapper in NSIS template).
