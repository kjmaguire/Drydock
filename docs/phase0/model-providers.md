## A. OpenRouter

### Findings

1. **OpenAI-compatible, with extensions. VERIFIED.** `api_reference/overview.mdx`: "OpenRouter's request and response schemas are very similar to the OpenAI Chat API, with a few small differences." Endpoint `POST https://openrouter.ai/api/v1/chat/completions`. Request supports `tools`, `tool_choice`, `stream`, `response_format`, `provider`, `models` (fallbacks), `session_id`. Tool calling guide: `guides/features/tool-calling.mdx` ("OpenRouter standardizes the tool calling interface across models and providers"; "The `tools` parameter must be included in every request").
2. **Usage accounting is always on. VERIFIED.** `cookbook/administration/usage-accounting.mdx`: "OpenRouter automatically returns detailed usage information with every response, including: ... Cost in credits ... Cached token counts". Streaming: "included in the last SSE message". "The `usage: { include: true }` and `stream_options: { include_usage: true }` parameters are deprecated and have no effect." Schema `ChatUsage` (openapi.yaml L8095): `prompt_tokens`, `completion_tokens`, `total_tokens`, `cost`, `cost_details.{upstream_inference_cost,...}`, `is_byok`, `prompt_tokens_details.{cached_tokens, cache_write_tokens}`, `completion_tokens_details.reasoning_tokens`. In streaming, the usage chunk has one choice with an empty delta repeating `finish_reason` (`api_reference/streaming.mdx`, "The final usage chunk (Chat Completions)").
3. **Rate-limit headers: NOT on success responses (contradicts a common assumption).** `api_reference/limits.mdx`: "Successful inference responses do not include `X-RateLimit-*` headers. When OpenRouter itself returns a 429 ... the error response carries `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` headers ... When every attempted provider returned a retry hint, the error response also carries a `Retry-After` header. To monitor your remaining quota before hitting a limit, call `GET /api/v1/key`." `Retry-After` is also sent on 503 and on 402 when `limit_source` is `openrouter_in_flight_budget` (`api_reference/errors-and-debugging.mdx`, "Retry-After header"). A 429 may be OpenRouter's own or the upstream provider's (`error.metadata.provider_code`).
4. **`GET /api/v1/key` is the pollable quota source. VERIFIED.** Fields: `limit`, `limit_remaining`, `limit_reset`, `usage`, `usage_daily/weekly/monthly` (UTC), `byok_usage*`, `is_free_tier`, `free_model_daily_requests.{used,limit,remaining}`, `allowed_data_regions`, `is_management_key`, `expires_at`; `rate_limit` is "deprecated ... safe to ignore". It contains NO privacy/data-policy fields (checked the full response example and schema, openapi.yaml L42834-L43140).
5. **Free-model limits: claim CONFIRMED.** `api_reference/limits.mdx` + `snippets/exports/constants.mdx` L107-113: `FREE_MODEL_RATE_LIMIT_RPM = 20`, `FREE_MODEL_CREDITS_THRESHOLD = 10`, `FREE_MODEL_NO_CREDITS_RPD = 50`, `FREE_MODEL_HAS_CREDITS_RPD = 1000`. Table: credits purchased all-time < 10 -> 20 rpm / 50 rpd; >= 10 -> 20 rpm / 1000 rpd. Nuance (VERIFIED, same page): "the higher daily ceiling is granted starting one credit below the table's threshold (currently 9 credits)". Per-minute count is not reported by `/key` ("The per-minute limit is not reported there"). Negative balance gives 402 "including for free models". Also: "Making additional accounts or API keys will not affect your rate limits".
6. **`:free` suffix. VERIFIED.** `guides/routing/model-variants/free.mdx`: "Append `:free` to the ID of a model that has a free entry ... only models that list one support it". `openrouter/free` router picks a random free model (`guides/routing/routers/free-router.mdx`) which is a poor fit for a data-class-aware router (provider unknown per request).
7. **`:exacto`. VERIFIED.** `guides/routing/model-variants/exacto.mdx`: "Exacto is a virtual model variant that explicitly applies quality-first provider sorting ... prefers providers with stronger tool-calling quality signals ... instead of using the default price-weighted ordering." "not backed by a separate endpoint pool". "If you explicitly sort by price, throughput, or latency, that explicit sort still takes precedence." Auto Exacto already runs on tool-calling requests (`guides/routing/auto-exacto.mdx`). Whether `:exacto` helps a single-provider model (e.g. Cohere free) is moot: "most useful on models that ... Have multiple providers".
8. **Privacy controls and per-request enforcement. VERIFIED.**
   - Per request: `provider: { "data_collection": "deny" }` (`guides/routing/provider-selection.mdx` L1180-1260; openapi `ProviderPreferences.data_collection` enum `deny|allow`). Quote: "`allow`: (default) allow providers which store user data non-transiently and may train on it; `deny`: use only providers which do not collect user data". "If no available model provider meets the requirement, your request will return an error."
   - Per request: `provider: { "zdr": true }` (`guides/features/zdr.mdx`): "the request will only be routed to endpoints that have a Zero Data Retention policy". It is an OR with account/guardrail settings: "the per-request parameter can only be used to ensure ZDR is enabled for a specific request, not to override or disable account-wide or guardrail enforcement." Providers that do not retain also cannot train, but some "do not train on your data but *do* retain it" -> `data_collection:deny` and `zdr:true` are different guarantees.
   - Fail-closed default for unknown policy: "If OpenRouter is not able to establish or ascertain a clear policy for a provider or endpoint, we take a conservative stance and assume that the endpoint both retains and trains on data" (zdr.mdx).
   - Account-level toggles: `provider-logging.mdx` "you can set whether you would like to allow routing to providers that may train on your data ... There are separate settings for paid and free models." Guardrail object exposes `enable_paid_model_training`, `enable_free_model_training`, `enable_free_model_publication` ("Whether this guardrail allows free endpoints that publish prompts") (openapi.yaml L9400-9430) plus `enforce_zdr_{anthropic,openai,google,xai,other}`. Guardrails are managed with a management key. A secondhand forum listing of the UI labels: "Enable paid endpoints that may train on inputs / Enable free endpoints that may train on inputs / Enable free endpoints that may publish prompts / Enable 1% discount on all LLMs / ZDR Endpoints only" (search snippet).
   - Not API-queryable: the account-level privacy page toggles are not in `GET /key`, and no `/privacy` path exists in the OpenAPI (path list checked). What IS queryable: `GET /api/v1/models/user` ("List models filtered by user provider preferences, privacy settings, and guardrails") and `GET /api/v1/endpoints/zdr` (list of ZDR endpoints). Guardrail fields via management key.
   - **Consequence for `private` enforcement**: a router can enforce it in code per request by always sending `provider.data_collection:"deny"` (and `zdr:true` for strict), because request-level values can only tighten policy. It cannot read the account toggles; do not rely on them. Also never send `X-OpenRouter-Cache` for private data (response cache stores completions at OpenRouter; default TTL 300 s, `guides/features/response-caching.mdx`).
   - ZDR scope warning: "ZDR enforcement only applies to provider routing for inference requests. It does not apply to plugins and tools you choose to enable, such as web search."
9. **OpenRouter's own data handling. VERIFIED (docs) + SECONDARY (ToS).** `guides/privacy/data-collection.mdx`: "OpenRouter does not store your prompts or responses, unless you opt in" to (a) Private Input & Output Logging, (b) "OpenRouter Use of Inputs/Outputs ... 1% discount". Both "Off by default". Metadata (tokens, latency) is stored. Terms-of-service text itself (openrouter.ai/terms) was not retrievable; search snippet reports: opt-in logging grants OpenRouter "a worldwide, perpetual, irrevocable, royalty-free license" (§6.2) and "perpetual license to use your Inputs in anonymized form for user metrics" (§6.5). ## B. Cohere North Mini Code 1.0

### Findings (all VERIFIED unless stated; source `hf://models/CohereLabs/North-Mini-Code-1.0` via HF connector, repo `updated_at` 2026-06-15, not gated)
- **Exists.** Model card: "North Mini Code is an open weights research release of a 30B-A3B parameter model optimized for code generation, agentic software engineering, and terminal tasks." Developed by Cohere and Cohere Labs. Architecture `Cohere2MoeForCausalLM`, 49 layers, 128 experts / 8 active, sliding-window 4096 with 3:1 sliding:global layers (`config.json`).
- **License.** README front matter `license: apache-2.0`; text "License: Apache 2.0". (No separate LICENSE file in the repo listing.)
- **Context/output.** "Context length: 256K & 64K max output". Note inconsistency: card's vLLM command uses `--max-model-len 320000`, `config.json` has `max_position_embeddings: 500000`, OpenCode config declares `context: 256000, output: 64000`. Use 256000/64000 as the supported figures.
- **Sampling.** "We recommend using the following set of sampling parameters for generation: `temperature=1.0`, `top_p=0.95`." Benchmarks run "using temperature=1.0 and top_p=0.95". `generation_config.json` contains no sampling defaults (only bos/eos/pad ids), so servers will NOT supply these for you; the app must send them. (vLLM would apply `generation_config.json` by default, per its docs, but this file has nothing to apply.)

- **Interleaved thinking.** "supports interleaved thinking and works best when turned on. ## C. Google AI Studio / Gemini API (OpenAI-compatible endpoint)

### Findings
- **Endpoint exists and behaves as OpenAI-style (live probe, VERIFIED).** `POST https://generativelanguage.googleapis.com/v1beta/openai/chat/completions` without a key returns HTTP 400 `{"error":{"code":400,"message":"Missing or invalid Authorization header.","status":"INVALID_ARGUMENT"}}`; with a fake bearer: 400 "Please pass a valid API key". `POST .../openai/embeddings` exists (a chat-shaped body gets "Unknown name "messages": Cannot find field", i.e., embedding schema; with a fake key the same "Please pass a valid API key"). **Gotcha: an invalid key is HTTP 400, not 401.** `GET .../openai/models` returned 404 "Requested entity was not found" unauthenticated; whether it works with a key is UNVERIFIED (docs page says supported, search snippet).
- **Coverage per official docs (search snippet of ai.google.dev/gemini-api/docs/openai; page itself unreachable):** chat completions, streaming (`stream=True`), function calling (`tools`, `tool_choice:"auto"`), image input (base64), structured output via `parse`, `reasoning_effort`. Explicit caching via `extra_body` -> `cached_content`. Usage: `usage.prompt_tokens_details.cached_tokens` reported by some responses per forum report but "The official OpenAI-compatibility page I found doesn't document `cached_tokens`" (search snippet) -> treat cached-token reporting as UNVERIFIED; the native `usageMetadata` has `cachedContentTokenCount` ("Number of tokens in the cached part of the prompt", discovery doc v1beta rev 20261006).
- **Free-tier limits per model: UNVERIFIED.** Official rate-limit page (search snippet): "Rate limits are applied per project, not per API key"; "Requests per day (RPD) quotas reset at midnight Pacific time"; "Limits vary depending on the specific model being used"; limits "can be viewed in Google AI Studio" and "specified rate limits are not guaranteed". No table was retrievable; forum numbers conflict (Flash 10 rpm/250 rpd in Jul 2025 vs 5 rpm/20 rpd later; Pro 5 rpm/100 rpd vs 50 rpd; some models have limit 0 on free tier). Design implication: **free-tier limits for Gemini must be user-configured or learned from 429 bodies**, not hardcoded.
- **Training terms (search snippets of ai.google.dev/gemini-api/terms; page unreachable, so quotes are snippet-level):**
  - Unpaid: "Any Services that are offered free of charge like direct interactions with Google AI Studio or unpaid quota in Gemini API are unpaid Services." Google may use submitted content to improve products; "human reviewers may read, annotate, and process your API input and output ... disconnecting this data from your Google Account, API key, and Cloud project"; "do not submit sensitive, confidential, or personal information to the Unpaid Services".
  - Paid: access is paid only "when accessing the API through a Cloud Project associated with an active billing account"; Google "doesn't use your prompts or responses to improve our products" and processes under a DPA; still logs "for abuse detection ... for a limited period of time". EEA/CH/UK: Paid-services data terms apply to all services even free quota.
  - ZDR page (search snippet of ai.google.dev/gemini-api/docs/zdr): paid services keep prompts/responses for a limited time only to detect Prohibited Use violations; "If your workload requires guaranteed zero data retention ... use Vertex AI"; Search/Maps grounding stores data 30 days with no way to disable; implicit cache is in RAM with a 24 h TTL and "does not violate ZDR"; explicit caches stored for user TTL.
  - Interactions API retention 55 days paid / 1 day free (search snippet).
- **Is a paid key with no-training terms a sensible `private` route?** Yes, conditionally: terms say paid use is not used for product improvement and has no human review of content for training, but (1) abuse-monitoring retention remains, (2) it is "paid" only if the key's project has an active billing account, and the app cannot verify that from the key (no API found; UNVERIFIED), (3) grounding/Interactions/File API/caching features change retention. Recommend `private` only when the user explicitly attests a billing-linked key AND the app disables grounding, Interactions `store`, File API, and explicit caching for private-class requests.

## D. Anthropic and OpenAI direct APIs as `private` routes

### Anthropic (VERIFIED, primary)
- **Training:** Commercial Terms of Service, Effective June 17, 2025 (https://www.anthropic.com/legal/commercial-terms, fetched 2026-10-08, §B Customer Content): "Anthropic may not train models on Customer Content from Services." Retention doc (https://platform.claude.com/docs/en/manage-claude/api-and-data-retention): "Retained data is never used for model training without your express permission." and "Conversation content (your prompts and Claude's outputs) is not retained by default; the exception is Covered Models ..., which require 30-day retention."
- **Covered Models** (same page): "Claude Fable 5.1, Claude Mythos 5.1, Claude Fable 5, and Claude Mythos 5 are designated Covered Models ... and require 30-day data retention; ZDR is therefore not available for any of them". Requests from an org without retention enabled return `400 invalid_request_error: "In order to access this model, your organization or workspace must have data retention enabled."` -> the router must map this error to a clear "enable retention or pick another model" message, and a `private` rule that demands zero retention must exclude these models. Even with ZDR, flagged content "may retain inputs and outputs for up to 2 years".
- **Prompt caching** (https://platform.claude.com/docs/en/build-with-claude/prompt-caching):
  - Mechanism: `cache_control` on a block, or one top-level automatic `cache_control`. Prefix order "`tools` -> `system` -> `messages`".
  - TTL: "By default, the cache has a 5-minute lifetime. The cache is refreshed for no additional cost each time the cached content is used." 1-hour TTL is an option "at additional cost" (price table: e.g. Sonnet 4: 5m write 1.25x, 1h write 2x, read 0.1x; "All other models use the standard 0.1x multiplier" except footnoted exceptions). "The lifetime is measured from the start of the request that writes or reads the cache entry, not from the end of its response."
  - Minimum cacheable length (Claude API): 512 tokens for Fable 5.1 / Mythos 5.1 / Opus 5.5 / Opus 5 / Sonnet 5.5 / Fable 5 / Mythos 5 / Haiku 5.5; 1,024 for Opus 4.8, Sonnet 5, Sonnet 4.6, Sonnet 4.5; 2,048 for Opus 4.7 and Mythos Preview; 4,096 for Opus 4.6, Opus 4.5, Haiku 4.5. "Shorter prompts cannot be cached ... no error is returned"; detect via `cache_creation_input_tokens` and `cache_read_input_tokens` both 0.
  - Isolation: "Caches are isolated per workspace ... on the Claude API"; "Cache hits require 100% identical prompt segments".
  - Invalidators: tool definition changes, speed setting, thinking parameters, effort setting, images, `tool_choice` (see table in the doc).
- **Rate-limit headers** (https://platform.claude.com/docs/en/api/rate-limits): `retry-after` ("The number of seconds to wait until you can retry the request. Earlier retries will fail. Not sent with the spend-cap 429"), `anthropic-ratelimit-{requests,tokens,input-tokens,output-tokens}-{limit,remaining,reset}` (reset = RFC 3339). Errors doc: 529 `overloaded_error`. Org/workspace limits are also readable via the Rate Limits API (`/docs/en/manage-claude/rate-limits-api`, not fetched; needs an admin credential, UNVERIFIED details).

## G. Prompt cache behavior across model changes in a session

- **Anthropic (VERIFIED, first-party Claude Code docs, https://code.claude.com/docs/en/prompt-caching, fetched 2026-10-08):** "Model: each model has its own cache. Switching models recomputes the entire request even when the content is identical." and "Each model has its own cache. Switching with `/model` means the next request reads the entire conversation history with no cache hits, even though the content is identical." Platform docs add exact-match and workspace isolation (section D) but contain no standalone sentence on model switching; the Claude Code doc is the explicit quote. Also changing `thinking`, `effort`, tool definitions, `speed` invalidates (platform doc "What invalidates the cache"). 5-minute default TTL, 1 hour optional.
- **OpenAI (partly UNVERIFIED):** no first-party sentence "cache does not survive a model switch" was retrievable. What is documented (spec + snippet): caching is automatic, exact-prefix, >= 1024 tokens; routing by prefix hash and `prompt_cache_key`; retention `in_memory` (about 5-10 min, up to 1 h) or `24h`/`ttl`; "a prefix that qualifies for caching on one model may be too short on another" (snippet of the guide). A secondary source states caches are keyed by model. Treat as "cache does not carry over" but do not cite OpenAI as the source.
- **Gemini:** Explicit caches are model-bound. VERIFIED from the v1beta discovery document (revision 20261006): `CachedContent` - "Cached content can be only used with model it was created for." and `model`: "Required. Immutable. The name of the `Model` to use for cached content". Implicit caching (2.5+; search snippet): on by default, 75% discount on cached tokens (read multiplier 0.25 per OpenRouter's constants), minimum token counts differ by model and source (1024/2048/4096 reported; conflicting), TTL "on average 3-5 minutes" via OpenRouter docs; per-model by construction.
- **OpenRouter (VERIFIED, `guides/best-practices/prompt-caching.mdx`):** sticky routing is per account, per model, per conversation: "Subsequent requests for the same model are routed to the same provider, keeping your cache warm." "Sticky routing is tracked at the account level, per model, and per conversation." Conversation id = hash of first system/developer + first non-system message, or explicit `session_id` body field / `x-session-id` header (<= 256 chars), falling back to `prompt_cache_key`. "Sticky sessions expire after 10 minutes of inactivity." Not used when `provider.order` is set. Sticky only activates when cache read pricing is cheaper, and "without `session_id`, sticky routing only activates after a cache hit is detected". For router models (`openrouter/auto`, pareto) the resolved model is reused only "on a best-effort basis ... The cache hint is ignored when it falls out of that set". Hence a model change = new (model) key = cold cache. Pass-through: `cache_control` for Anthropic/Gemini/Alibaba, automatic for OpenAI/DeepSeek/Grok/Moonshot/Groq; Anthropic cache reads 0.1x / 5-minute writes 1.25x / 1-hour writes 2x of input price; Google reads 0.25x (constants.mdx).
- **Local hosts:** vLLM automatic prefix caching and SGLang RadixAttention are keyed to the loaded model's KV; switching to a different model on the same server is a different engine/model and cannot reuse KV (logical consequence, not a quoted statement). Ollama unloads models after `keep_alive`.

Design implication: treat "switch model mid-session" as costing one full uncached prompt (input-price x context); ledger should estimate that cost before an automatic downgrade/upgrade, and prefer switching only at natural breaks (compaction, new task). Keep `session_id`/`x-session-id` stable per conversation when going through OpenRouter.
