# Drydock: UI information architecture

Scope: this document turns brief section 21 into an implementable UI plan for Slices 1A to 1E: the four-region layout, every screen that exists in those slices, the screens that must be shown honestly as "not built yet", the component inventory (Monaco diff, React Flow, cmdk, TanStack Virtual, xterm.js), message card types, the Needs-you inbox, the Connections page, Providers settings, the Agent Inspector, the Wails v3 integration contract (services, events, generated bindings, replay by event `seq`), keyboard map, theming, state management, streaming performance rules, accessibility basics, and a slice-by-slice delivery table. Owner decisions in `decisions.md` (D1-D14, P1-P6) win over the brief. Facts about Wails come from `phase0/go-platform.md` section 1; anything not in the brief, decisions or appendices is marked **proposal** (a design choice made here) or **unverified**. Nothing in this document has been run on Windows (P2).

**Status (what exists, honestly), 2026-10-09: rebuilt on Remix 3 (decision P25).** The UI in `ui/app` is a browser-only Remix 3 app: `remix` 3.0.0 components and SPA router (path routes, the Navigation API; the Go side serves `index.html` for app paths, `internal/uiassets`), `@remix-run/ui` headless widgets wrapped in our own kit, Lucide icons and Inter bundled, built by Vite 8 with Pitlane's Remix plugin in SPA mode (component hot reloading in `npm run dev`). React, React Flow and cmdk are gone: the workflow graph is our own SVG (pan, zoom, fit, keyboard navigation) and the Ctrl+K palette is our own dialog. Monaco and xterm stay, loaded lazily. The design is one Linear-style sidebar (a monochrome Drydock mark and a **project switcher** menu at the top, then screens, channels named with icons rather than `#`, and the workspace pages) around dense pages and a compact comment-thread conversation, with a details panel on the right and the dock at the bottom; the Discord-style project rail is gone. Light and dark come from one set of `light-dark()` tokens. **New projects are made with a wizard** (`/project/new`, also the first run): Basics (name, brief), Repository (GitHub through the user's own `gh` with an owner select, search and clone folder; a local folder; or Later), Connectors (library and built-in MCP servers), Team (prebuilt agents from the catalog, custom agents and templates, each with its agent CLI, model, effort and permission mode; a Team Lead, an engineer and a Code Reviewer suggested) and Review, sent as one `project.setup`; what failed after creation is listed as warnings before the project opens. **A project from scratch (decision P58):** the local folder field (the wizard's and Project settings' attach form, `screens/project/folder-field.tsx`) has **Choose folder…** for the window's own folder dialog (`fs.pickFolder`; shown only where the window has one) and still takes a typed path; its hint recommends a Windows Dev Drive and names the ones found (`fs.folderHints`); a moment after the path changes it says what is there (`repo.check`: a repository on its branch, a folder that is not one, one that does not exist yet, one inside another repository, which blocks Next with the reason), and for a plain or missing folder offers **Create a Git repository here** (the wizard sends `repo.init: true` in `project.setup`; the attach form calls `repo.init` before `project.attachRepo`). An agent CLI ready only inside a WSL distro is offered as available with the distro named. **A project can exist without a repository**: Project settings then says so and attaches one once (a local folder, or a GitHub repository cloned with gh), delivery mode is off, Pull Requests asks for a GitHub repository and the dock offers no repository terminal. The brief is edited in Project settings. The Team page adds prebuilt agents (`agentcatalog.apply`, with skills and connectors) and the Library lists the catalog read-only. **Skills are chosen with the agent** (decision P35): the new-agent and edit-agent forms have a Skills section (the project's accepted skills, the ones the whole team gets for the role shown as included), the agent template form lists and adds the registry skills a template brings, and the open skill's panel on the Skills page says who gets the skill (the whole team or its roles, agents given it on top, or only chosen agents) with "Change who gets" to set it. **The skill Library and the Skills page as tiles (decisions P48 and P49, 2026-10-13).** The core fills a workspace skill library from every enabled registry by itself (at start and twice a day, `skill.libraryList`, `skill.registryStatus`, re-read on `skill.library_synced` and `skill.registry_updates`); a project no longer imports from the network, it **adds** skills from the Library, and adding is the person's acceptance (`skill.libraryAdd` returns the skill accepted). The Skills page (`/skills`, `ui/app/screens/skills/skills-screen.tsx`) uses the shared tile kit (`ui/app/ui/tiles.tsx`) with the registry's brand logo (`SKILL_BRANDS` in `skills.ts`; a repository skill shows a file icon), like Integrations and Connections: **In this project** is a tile per project skill whose state line reads "Accepted ✓ · whole team" or "Accepted ✓ · 2 agents", "Offered", "Rejected", "Blocked" or "Update in the Library" (when `registryStatus.projects[pid].updates` names it); clicking a tile opens its panel below the grid (the text rendered inert, who gets it, Accept and Reject for an offered skill, **Stop using** with a confirmation for an accepted one, Release for a blocked one, **Update from the Library** when the Library's text is newer, and when it was last delivered). **Add from the Library** lists the Library's skills the project does not have yet, with a registry chooser (All, then one chip per registry with its count), each tile saying Available or "Blocked: <reason>" (a blocked skill has no Add button); **Add to project** shows a success status with a check ("wrangler was added to gocalc and is accepted ✓", `role="status"`, test id `skill-added`) and the skill's tile moves to the project with its check; **Add all from <repo>** (`skill.libraryAddAll`) reports how many were added, unchanged, blocked or skipped, with the reasons; an empty Library says it is filling and offers **Sync now**. **Usage** (`skill.usage`, re-read on `skill.used`) is a table, not tiles: skill, loaded (the full text went into a run), listed (named for on-demand reading), opened (an agent read it), tasks, tokens (loaded plus listed, with thousands separators), last used, and the core's recommendation as a badge (remove, with its reason and a Stop using button; narrow; keep; or "no data yet"), the ones to remove first, then by tokens. **Registries** are tiles too (logo, repository, "N skills in the Library (M blocked) · synced <time>", "Not synced yet", "Last sync failed: <reason>" or "Disabled: not synced"); the open registry's panel lists what the last sync added and changed, names the project's skills that are behind the Library, and offers Sync now (`skill.registryCheck`), Enable or Disable, Remove (for a registry added by the person) and the "Allow another repository" form; the per-skill Import buttons and the candidates list are gone. The Library page (`/library`) gains a **Skills** section with the same registry tiles; the selected registry lists its skills as tiles with "In <project> ✓" on the ones the chosen project already has (a project select that starts on the current project), **Add to <project>** with the same `skill-added` status, and **Add all to <project>**; the template panel's skill chips carry a check for the skills the current project already has. **The team lead** (an agent with the role `lead`): Run stand-up on the Team page and in the details panel (`lead.standup`, posted in #general), its interventions on the Team page and on each task page (`lead.interventions`, live on `lead.intervened`), and its stall time in Project settings (`leadStallMinutes`). **The limit question and watchdog pauses** are answered on the task page with Continue (optional guidance) or Stop, with the lead's recommendation shown first when it looked; Needs you says which is which. **The pull request's gates** are answered there too: the CI gate (no CI reported, a required check missing, or CI still running) with Check CI again, Merge without CI this time or Stop, and the merge gate (GitHub would not merge: branch protection, behind, conflicts, a draft) with Check again or Stop. Project settings has **CI before merge** (Required, or "This repository has no CI: merge after the review alone", showing who declared it and when; docs/github.md section 5). **Chats** (`/chats`, `/chats/:id`, decision P29, contract in [`chats.md`](chats.md); a sidebar item that is there with or without a project, and New chat plus the recent chats in Ctrl+K): a list column (chat.search with highlighted matches, pinned first, the current project's chats or All chats, archived on request; a row menu to pin, rename, fork, archive, or delete after a confirmation) and the conversation. Streamed text (`chat.delta`) fills an in-progress bubble that sits outside the `role="log"` live region, so only stored messages are announced; tool calls are compact rows with the input collapsible; a refusal is a callout with the suggested rule, "Allow for this chat" (`chat.allowTool`) and then Retry; system notes and errors are quiet lines. The header has the inline title, adapter, model, effort and permission-mode chips with a settings popover (a mode that skips approvals is marked and warned about), the folder, the session status, tokens and a cost that reads "cost unknown", never $0, when no turn reported one, Fork, and the allowed tools (remove, or add a rule). The composer sends with Ctrl+Enter, attaches up to five other chats as removable chips (their history goes with that one message), and offers Stop while a turn runs (a send is not possible then). Older messages page in on scroll-up. The new chat dialog takes the project (or no project with an absolute folder, checked before sending), the agent CLI (Claude Code first; CLIs that are not installed are listed disabled with the reason), model, effort, permission mode and "Let this chat read my other chats" (on). Not verified: a real Claude Code chat from the UI (the e2e uses the scripted agent), a real ACP chat, Windows. Conventions: `ui/app/README.md`. Every screen listed below exists in the new UI with the behavior it had before (the e2e suite is the contract for labels, roles and test ids).

Transport: `ui/app/api/transport.ts` (HTTP + Server-Sent Events) and `ui/app/api/wails.ts` (chosen by `main.tsx` when a WebView2/Wails host is detected, otherwise HTTP). Start-up is exact: read `events.head`, open the stream after it, then let screens read their projections; screens re-read on matching events and once each time the stream opens again after a break (`ui/app/state/eventStore.ts` bumps `epoch` in `onOpen` when the open follows a failure, never while the core is unreachable; `ui/app/state/live.ts` re-reads on `epoch`). The Wails transport has no end-of-stream signal from the shell, so it detects a break itself: Subscribe failing, any call that cannot reach the bridge, and a heartbeat (`events.head` every 15 s) that fails or finds the core holding events the stream has still not delivered one heartbeat later; Wails call rejections keep their meaning (`RuntimeError` is the core's refusal, `bad_request`; an unknown core method `not_found`; a panic `server`; an unreachable bridge `network`), tested against a labelled test double of the runtime only. **Tested (2026-10-11):** 695 `remix test` tests (Node unit tests and component tests in a real Chromium page) and 33 Playwright tests that drive the real Go core (`cmd/drydock-e2e`; the scripted fake agent and an in-memory credential store are the only test doubles) in Chromium on Linux, covering the product loop (approve, request changes, reload equality), threads, DMs, archived channels, the inspector, the dock (Monaco diff, logs, a terminal), the workflow graph and checkpoints, the composer and palette, budgets, evals, routing, telemetry, licensing (unconfigured, expired, active), backups and restore staging, export and import, the support bundle, the MCP library with drag and drop and OAuth, integrations, the collision guard, XSS and chats (create, reply, reload, resume, a refused tool allowed and retried). **Accessibility, measured (2026-10-11):** an axe-core 4.13 scan (WCAG 2.1 A/AA plus best practice) of 31 screens against the real core, light and dark, went from 455 violation nodes in 9 rules in the light theme and 423 in the dark (colour contrast 380 and 348, an invalid `aria-controls` on 31 screens, the skip link outside a landmark, prose links told apart by colour, unnamed Monaco editors, unreachable scrolling tables, the evals `<dl>`, the Connections heading order, the composer's `role="combobox"`) to none in either theme; the colour tokens are checked by `ui/app/styles/contrast.test.ts` (every text pair at least 4.5:1 in both themes). **Not verified:** anything in WebView2 or on Windows (Navigation API interception, the Go index fallback on a reload, Monaco workers under the Wails asset server, the CSP in WebView2, the Wails transport's error shapes and stream-break detection, forced-colours mode); a screen reader; the pre-existing gaps listed in earlier revisions of this paragraph (a staged restore applied after a restart, the licensed grace state, vendor-backed integrations, GitHub screens against GitHub) still hold.

**MCP connectors and prebuilt agent details (decision P43, 2026-10-12).** The MCP servers page (`/mcp`, `ui/app/screens/mcp/gallery.tsx`) opens with **Connectors**, shown with or without a project: a card per catalog server (`mcplib.gallery`) grouped as hosted servers, a vendor group (Cloudflare: documentation and API), and "Programs you run on this computer" (the GitHub, Sentry and Aikido user-install templates, each showing the command it starts). A connected card lists its tools (read-only or "asks you first"), the server's instructions as text, the projects it is in, and offers **Add to project** (a project select), **Grant to agents** (the current project's agents as checkboxes) and **Disconnect** (with a confirmation). A card whose brand also has a Drydock integration links to it ("Drydock also imports Linear issues: Integrations"); the Integrations screen itself is not changed here. Below, **Your own servers** shows each server the human described by what it says about itself ("Identifies itself as Acme Tracker (acme-tracker 3.2.1)", its instructions, its tools, its last error) with Test connection; **Add your own server** opens the server form and then reaches the server once to learn its identity; **Import from a file** reads a pasted or picked `claude_desktop_config.json`, Cursor `mcp.json` (`mcpServers`) or VS Code `mcp.json` (`servers`), shows each server as a card with what it runs or reaches and which values go to the credential store (every environment value and a bearer token), says why an entry is not taken (`${...}` placeholders, the old SSE transport, neither command nor url), and imports the chosen ones. With a project, the page then shows the calls waiting for approval and the project's servers as before. **Prebuilt agents** (`ui/app/screens/team/agent-gallery.tsx`, used by the Library, the Team page and the new-project wizard): an MCP badge shows the server's logo and full name (for example "Context7") with a tooltip naming the publisher and what it does; the skills badge lists the skills in its tooltip and accessible name; the agent's name, the skills badge and **Details** open a dialog with the model, effort and CLI (and whether it is installed), each skill with the description from its SKILL.md at the pin, the source repository linked at the pinned commit, the short commit and the license, and each MCP server with its logo, publisher and summary; with an Add button the dialog can add the agent too. Tested: `gallery.test.browser.tsx`, `import.test.ts`, `agent-gallery.test.browser.tsx` in Chromium, and `ui/e2e/round16.spec.ts` against the real core (Connect with OAuth against the harness's fake OAuth server, Connected as its account, Add to project, Grant to agents, Disconnect; the prebuilt details in the Library). *Since decision P47 (next paragraph) the connector cards, your own servers and the project's servers described here are on the Integrations page; the MCP servers page no longer exists on its own. ## 1. Principles (from brief sections 0, 16, 21)

- Dense, keyboard-first, dark and light, restrained motion. Slack/Discord information architecture with engineering panels.
- **Build only screens for features that exist** (brief 0, 21). No screen, tab, or button ships ahead of its slice. Where a user would reasonably expect a feature, the UI states that it is not built yet and names the slice (section 4). No fake data, no placeholder charts, no simulated agents (brief 0).
- **All agent output, room messages, GitHub text and retrieved content are untrusted** (brief 16). Markdown is rendered through a sanitizer with raw HTML disabled, remote images are not auto-loaded, links open in the external browser after showing the target, and text can never trigger an approval. Approvals are answered only by buttons bound to an approval id (brief 12: bound to a hash of the exact action).
- The UI holds no authority: SQLite is the single authority (brief 3). The UI is a projection of persisted events plus service calls; it can be closed and reopened at any time and must catch up from the log (brief 24, Slice 1A).
- Estimated and reported numbers are never mixed silently (brief 7): every token or cost figure carries a source badge (`reported` or `estimated`), and a value a CLI does not report is shown as `not reported`, never as 0.

### 6.1 Monaco diff
Read-only `DiffEditor` for task diffs (original = merge base or safe-point ref, modified = worktree), inline and side-by-side toggle, file list with +/- counts, per-file collapse, jump to next change. Large diffs: load per file on demand; files over a size threshold (**proposal**, tune after measurement) render a "large file" placeholder with an explicit "render anyway" button. Models are disposed when a file leaves view. Theme follows the app theme (section 12). Inline comments and "Ask Agent about this hunk" arrive with 1D review; no edit-in-place in Slice 1. Bundling Monaco workers under the Wails asset server is **unverified** (needs a spike in 1B).

**As built (2026-10-09).** `ui/app/screens/dock/diff-viewer.tsx` + `monaco-diff.ts` (monaco-editor, lazy chunk; only the editor API, the
diff editor, find, folding, copy, context menu and the language definitions are imported; links are not, since file content is
untrusted). The core serves `task.diffFiles` (the files of the recorded diff, or of the live worktree) and `task.diffFile` (both
versions of one file: the base and task commits from git, or the file on disk for a live diff, refusing paths outside the

### 6.2 Workflow graph with checkpoint timeline (Slice 1C; planned with React Flow, built as our own SVG)
- Nodes by kind (brief 4): `agent_task`, `check`, `request`, `route`, `subworkflow` (a subworkflow node expands into a nested graph view). Edge kinds: direct, conditional, fan-out, fan-in (barrier), loop (drawn with iteration count and the limit, default five for Iterate Until Verified).

- Layout is computed deterministically (left-to-right layered) so a re-render does not move nodes; supersteps are columns. Positions are not persisted in Slice 1.
- **Checkpoint timeline** below the graph: one marker per checkpoint ordered by lineage (`parent id`), marker kind `entry`, `step`, `response_entry`; branches from time travel drawn as parallel lanes; latest checkpoint is authoritative for run state (brief 12). Selecting a marker puts the graph in read-only "as of checkpoint" mode (earlier checkpoints are never modified). Actions: Resume latest (after a crash), Time travel from here (starts a new lineage branch, confirmation), Replay from `entry`. A run lease holder indicator shows whether this instance owns the run (`run_leases`).
- Large graphs: only the active run's graph is mounted; node components are memoized; off-screen elements are not rendered (React Flow option for visible-only rendering, **unverified** against the pinned version).

**As built (2026-10-09), together with the run explanation (S16).** One page per task run, `/task/<id>/run[/<run id>]`

**Composer (brief 21; As built 2026-10-09).** `ui/app/screens/room/composer.tsx` with the pure helpers in `ui/app/lib/composer.ts`.
Typing `@` lists the room's members (and roles), `@role:` the roles, `#` the project's channels and task channels, `/` at the

### 6.4 Virtualised lists (planned with TanStack Virtual, built as our own kit module)
Used for: message lists (bottom-anchored, dynamic row height, "jump to latest" pill when scrolled up, no auto-scroll while the user has scrolled away), task lists, the event log, inbox, changed-file lists, logs. Rules: stable row keys (`id`), measured heights cached per id, overscan small (**proposal**: 6 rows), expanded/collapsed state stored outside the row component so recycling does not lose it, and `role="log"`/`role="list"` semantics with accessible names (section 14).

**As built (2026-10-11): the room feed and the chat feed are windowed by our own kit module; TanStack Virtual is not a dependency.** Paging: a room (`ui/app/screens/room/feed.ts`) reads its newest 100 messages first and older pages on scroll-up or "Load older messages". Each is one `room.messages` read: `latest` for the newest page and `beforeSeq` (the oldest seq shown) for the page above it, both answered oldest first and asked for one message more than a page, so the start of the room ("This is the start of the channel") is known without an empty read; `afterSeq` reads forward what was posted (`room.message_posted`) and what was missed while the stream was down, and more than a page of news starts the list again from the newest page. Chats page the same way (`chat.messages beforeSeq`). Windowing (`ui/app/ui/virtual-list.tsx`, its arithmetic in `ui/app/ui/virtual.ts`): of the loaded rows only those near the view are rendered, the rows above and below are padding of their height. Each rendered row sits in a `display: flow-root` box that is measured after render and watched by a ResizeObserver (images, an opened `<details>`, a new width); heights are kept per row key, and a row never measured counts as the mean of the measured ones (48 px before any). The window is the view plus an overscan of one view (at least 240 px) on each side, and is planned again only when the view comes within half an overscan of its edge, so scrolling re-renders about every half view, not on every scroll event. Bottom anchoring: while the reader is within 40 px of the bottom the list stays there (a new message, a row that grows, a smaller window); away from it the first rows in the view are the anchor (row key and distance from the top of the view), and after any change (an older page added above, a measurement that differs from the estimate, rows arriving below) the scroll position is corrected so the anchor row stays exactly where it was, so neither a prepended page nor new messages move what is being read. The browser's own scroll anchoring is turned off on the scroller so the position is corrected once. A scroll the controller makes itself is not read as the reader leaving the bottom, and a scroll the reader made whose event has not arrived yet wins over a correction. Room day dividers are keyed by the message they stand before, so a key names one place in the list. The "jump to latest" pill shows while scrolled away, with the count of messages that arrived below. Accessibility: the `role="log"` region announces only rows that are new: rows that enter the window because of scrolling, a re-plan or a page added above set it to `aria-live="off"` for two frames (the room's log is also off until its first page is on screen and while an older page loads); away from the bottom the newest rows are not rendered, so a visually hidden status says "N new messages below" instead. Focus: when the focused row leaves the window, focus moves to the scroller (it is focusable), not to the page; Tab reaches only rendered rows (the view and the overscan). A row's `<details>` keep their open or closed state across leaving and re-entering the window. Find in page (Ctrl+F) only finds rendered rows, about three views of the conversation around what is shown. Proved by the tests: 2,000 room messages read page by page (19 older pages) never put more than four views of rows in the DOM (asserted below 100 rows; 21 at most in a 417 px log in the run that added it), and every older page leaves the row at the top of the view where it was, within a pixel (`room-screen.test.browser.tsx`); the same for a 2,000-message chat (`chats-screen.test.browser.tsx`); the kit test covers 2,000 rows of 24 to 154 px, every row measured, rows arriving above and below, a row growing above the view, resizing, focus and `<details>` (`virtual-list.test.browser.tsx`). Markdown is lexed once per message (`memoLex` in `ui/app/ui/markdown.tsx`), and the room's rows are rebuilt only when its messages change, so a re-render for the window does not re-lex or regroup. Task lists, the event log, the inbox, file lists and the Logs dock render in full.

### 6.5 xterm.js terminal (Slice 1B)
One xterm instance per ConPTY session (go-pty, ConPTY, 80x25 initial then resize via `ResizePseudoConsole`). Output path: Go reads PTY, coalesces to frames, emits a typed event per terminal id (binary payload encoding **proposal**); the UI writes to xterm directly (never through zustand state) and acknowledges bytes consumed so Go can pause reading when the UI lags (flow control, **proposal**, measure on Windows). Input goes back by service call. The embedded terminal is also where CLI logins run (Connections, section 8) so Drydock never handles tokens. ANSI handling server-side uses `charmbracelet/x/ansi` only for stripping/width in logs (phase0 appendix 10); ConPTY re-renders and emits its own cursor sequences, which must be checked on Windows (unverified). Terminal tabs are killed with the process tree when closed.

**As built (2026-10-09).** `internal/terminal` (go-pty: ConPTY on Windows, a Unix pty elsewhere) behind `terminal.open/read/write/
resize/close/list`. A terminal opens in a task's worktree or a project's repository, never at a path the caller names. Output is
kept in a 1 MB ring per terminal and read by offset with a long poll (`terminal.read` waits up to 20 s), so both transports carry
it on the ordinary call path; a reader that falls behind is told how many bytes were dropped. Output is never written to the event
log or the database. There is no flow-control acknowledgement: the UI long-polls by offset and the ring drops what a slow reader missed. A failed poll is retried with backoff (250 ms doubling to 5 s, twelve tries, about 45 s) with a note in the terminal; only "no such terminal" or the retries running out end it. Closing a terminal ends its process tree: on Windows the shell is put in its own kill-on-close Job Object
right after it starts (`proc.AttachTree`; D7), on Linux the session is killed. The human's terminal inherits Drydock's full
environment (it is the human's shell, not an agent's). `ui/app/screens/dock/xterm-view.ts` (xterm.js 6 + fit addon, lazy chunk) writes
output straight into xterm. Up to 8 terminals at once. **Unverified on Windows:** ConPTY behaviour, PowerShell as the default
shell (pwsh when installed), the job assignment race for children started in the first instant.

The Logs tab (`ui/app/screens/dock/logs-panel.tsx`) lists a task's check logs (evidence rows with a log file) and agent streams (the
`stream.jsonl` of each node execution that streamed something) through `logs.list`, and reads them by byte range through
`logs.read` (the tail first, earlier output on request, new output followed while running). The log is one `<pre>` holding at most 5,000 lines in memory (not virtualized); it is a named, focusable `role="log"` with `aria-live="off"`, because its text is replaced on every poll and would otherwise be read out whole each time. An agent stream is rendered as
readable lines (text as it streamed, `[tool]`, `[result]`, `[usage]`, `[error]`); a log is named by an id Drydock gave it, never
by a path. The dock's open state, tab and height are kept per project; Ctrl+J toggles it and Ctrl+Shift+D opens the Diff tab (neither fires while focus is in the terminal or the diff editor, where Ctrl+J and Ctrl+K are the widget's own keys). The resize handle is a focusable `separator` with its range and value (Arrow Up and Down resize by 40 px).

## 11. Wails v3 integration (facts from `phase0/go-platform.md` section 1)

- Wails v3 is **beta** (`v3.0.0-beta.28`, pinned, MIT); `@wailsio/runtime` npm `3.0.0-beta.28`. Wails imports exist only in `app/` (brief 2, 20); `internal/` never imports `app/`.
- **Services:** `application.NewService(&T{})` or `NewServiceWithOptions(inst, ServiceOptions{Name, Route, MarshalError})`. Optional `ServiceStartup(ctx, options) error` (ctx cancelled just before shutdown; startup in registration order; an error aborts `App.Run`) and `ServiceShutdown() error` (reverse order). An instance implementing `http.Handler` is mounted on the asset server at `Route`. **Proposal:** one thin service per facade in `app/` (Project, Room, Agent, Task, Approval, Connection, Provider, Workflow, Review, Terminal, Event, Settings, Update, License), each delegating to `internal` interfaces; `MarshalError` maps domain errors to `{code, message, retryable}` so the UI never parses strings.
- **Events:** `app.Event.Emit(name, data...)`, `On(name, cb)` (returns unsubscribe), `OnMultiple`, `Off`; typed events through `application.RegisterEvent[Data](name)`, which validates payloads and feeds binding generation, so the TypeScript event payload types are generated, not hand-written. The Event Bus remains the in-process source (brief 10); Wails events are only the transport.
- **Bindings:** `wails3 generate bindings -ts` (flags include `-d dir`, `-names`). Observed output `frontend/bindings/<pkg>/<service>.ts` with functions such as `Greet(name): $CancellablePromise<string>` calling `$Call.ByID(<number>, ...)` from `@wailsio/runtime`; 259 packages and one service processed in 3.4 s. Calls are by numeric ID (names via `-names`). **Rules:** a Taskfile target regenerates bindings before every UI build; generated files are never hand-edited; CI fails if regeneration produces a diff. `$CancellablePromise` lets the UI cancel a call when a view unmounts.
- **Large payloads:** the `http.Handler` mount can serve range reads of raw output, diffs and artifacts (`GET .../raw/<run>/<node>/<attempt>?offset=&len=`) so big bodies do not travel through events. Seen in source, not exercised (**unverified**); the same channel must apply the output-truncation rule: long tool output is fetched by range, never preloaded (brief 7).
- **Event replay after reconnect (brief 10, 24):** every persisted event has a monotonic `seq`. Protocol (**proposal**): (1) the UI keeps `lastSeq` per window; (2) on startup, window reload, or focus after sleep, it subscribes first and buffers live events, then calls `EventService.Replay(afterSeq=lastSeq, limit)` repeatedly until it returns the head; (3) buffered live events with `seq <= lastSeq` are dropped, others applied in order; (4) every live envelope carries `seq` and `prev_seq` (the previous published seq), and a mismatch triggers another Replay instead of assuming gaplessness (the brief promises monotonic, not contiguous, sequence numbers); (5) the first launch reads a snapshot (current projections via services) at a known `seq` and replays from there. The UI never renders an event it has already applied. Acceptance for 1A: kill the UI process or reload the window mid-stream and the transcript is identical afterward; restart the app and the UI catches up from the log.
- Wails emit latency under streaming load and `ServiceStartup` ordering under crash restart are **unverified** on Windows (phase0 section 7, item 3). Single-instance support exists for Windows (`single_instance_windows.go`); Drydock must enable it because SQLite has a single writer and `run_leases` assume one engine instance.

## 13. State management (planned: zustand)

Choice: **zustand** (one store per domain: connection, rooms, agents, tasks, approvals, workflow, ui). Reasons: (1) selector subscriptions give per-component re-render control, which matters with a streaming transcript; (2) stores are usable outside React, so the Wails event handler writes straight into the store without a provider tree; (3) small, no boilerplate, easy to test in isolation; (4) no server-cache semantics are needed because the source of truth is the event log, not request/response caches (this is why TanStack Query is not adopted). Rules: store state is derived by a pure reducer `applyEvent(state, event)` shared by live events and replay, keyed on `seq`, so replay and live paths cannot diverge; service calls return snapshots that seed the store at a known `seq`; streaming text lives in an external buffer (section 15), not in the store; persisted UI preferences (theme, panel sizes, last room) go to the settings service, with `localStorage` only as a cache that may be empty.

**As built (2026-10-09): no zustand and no client-side domain store.** `ui/app/state/eventStore.ts` only opens the core's event stream, dedupes by `seq`, remembers the highest `seq` and reopens after a break; screens read the core with RPC calls and re-read when a matching event arrives or the stream opens again after a break (`epoch`, bumped in `onOpen`; `ui/app/state/live.ts`, `query` in `services.tsx`). Cross-region state lives in small models (`state/ui.ts`, `workspace.ts`, `project.ts`). UI preferences (theme, dock, details panel, collapsed sidebar groups, the selected project) are kept in `localStorage` only; nothing goes to the settings service. Conventions: `ui/app/README.md`.

## 15. Performance rules for streaming output

Targets are goals, not measurements; none has been measured (Windows only).
1. Coalesce in Go: token deltas are batched per run into frames (default window 30-50 ms, **proposal**) before being emitted; the UI never receives per-token events. Persisted events reference byte ranges in raw output on disk (brief 4) rather than carrying every delta, to protect the event table write rate (Linux numbers: 25k rows/s single-row commits, 141k rows/s at 1000-row batches; NTFS unmeasured).
2. Per-frame UI work is `O(visible)`: streaming text is appended to a buffer outside React and flushed to the in-progress card at most once per animation frame; only that card re-renders.
3. Markdown: finalized blocks are memoized and never re-parsed; only the trailing open block is re-parsed per flush. Code blocks highlight after the block closes.
4. All lists virtualized (6.4); a message body longer than a threshold shows head and tail with "show range" (fetch by range), never rendering megabytes.
5. Background rooms accumulate state but do not render; when a room is not mounted its events only update counters and last-message previews.
6. One event listener per event type at the app root, not per component; handlers do `O(1)` store writes and batch updates inside one `requestAnimationFrame` tick.
7. Terminal output bypasses the stores (6.5). Logs dock uses virtualization with a capped in-memory window (**proposal**: 5,000 lines) and fetches older ranges on scroll.
8. Heavy components (Monaco, React Flow, xterm) are code-split and mounted on first use; Monaco models and React Flow instances are disposed on unmount.
9. Backpressure: if the UI lags (frame budget exceeded for N flushes), the UI sends `Replay`-style resync and drops intermediate deltas of in-progress cards, because the raw output is on disk and authoritative.
**As built (2026-10-11):** rule 3 holds per message (each message's Markdown is lexed once, not per block). Rule 4 holds for the two message feeds: the room and chat feeds are windowed (6.4: the view and one view of overscan on each side are rendered, rows measured, the rest padding), so their DOM stays a few dozen rows however much history is loaded; the long-message head-and-tail rule, task lists, the event log and the inbox are not windowed. Rule 7 does not hold: the Logs dock is a capped 5,000-line `<pre>`. None of the frame and flush targets has been measured.

10. A performance test per slice measures events/s accepted, flush time, and dropped-frame rate with a synthetic-free source (a real agent run or recorded real stream), recorded in `evals.md` notes; no number is claimed before it exists.

The room's `role="log"` stays `aria-live="off"` until its first page is on screen and while older pages load, so opening a room does not read its history; streamed chat text sits outside the chat's log. Both feeds are windowed (6.4): rows revealed by scrolling or by a page added above turn the log's `aria-live` off for two frames, so only new rows are announced, and while the reader is away from the bottom a hidden status says how many messages arrived below. A room is marked read only while the window is visible and focused and the list is at the bottom. `Loading` is a `role="status"`. The skip link sits in its own `nav` landmark. Markdown tables scroll in a focusable group named after their columns. Monaco's two diff editors are named after the file (before and after the change). The Needs you count is in the sidebar and the window title; it is not announced. xterm's screen-reader mode is off. Not done: a screen-reader pass.
