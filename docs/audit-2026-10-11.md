# Drydock full audit, 2026-10-11

Audited at commit `a8d22fb` by four lenses the owner asked for (full-stack engineering, UI, AI systems, bots and automation) plus two that the "hard evidence, not hope" principle demands (security, test strategy and evidence trail). Section 2 says exactly what was run and what could not be. Every finding cites the file and line it rests on; every High was re-verified by the lead auditor. This document records the state of the code; it changes nothing.

## 1. Verdict

Drydock is built the way its brief demands: real processes, real git, real SQLite, a workflow engine whose crash-recovery and exactly-once claims are proven by kill-the-process tests under the race detector, approvals that only a human can answer and that are bound to a hash of the exact action, an MCP gateway and an egress proxy that fail closed, a UI that never renders raw HTML, and an evaluation ledger whose every published number recomputes from committed raw records. The CI history is honest too: 192 Windows runs, zero re-run attempts, failures fixed by the next push. For three days of work this is well above the bar most products ship at.

The gap between the design documents and the code is where the risk sits. Four documented security or robustness controls are not built (git hook neutralisation and config-drift detection, the environment scrub for check commands, the GitHub per-call timeout and idempotent PR creation, the `permission_prompt` binding), and several AI-layer behaviours the documents describe as done (context-pressure handoff, rate-limit consumption, ten named proving tests) do not exist. One parsing bug turns a valid reviewer `SHIP` into a paid `REVISE` whenever the feedback contains a brace. The UI's light theme fails WCAG AA on every screen, and the product's three most important test suites for a Windows desktop app (the browser end-to-end suite, the sandbox, the Claude adapter's process-level tests) run in no CI workflow or skip on the only CI platform.

None of this is "hopes and prayers"; it is a project that writes its intentions down before building them and has not yet gone back to mark which intentions are still intentions. The fixes are small and well-located (one git chokepoint, one environment builder, one regex, one `onOpen`, one colour palette, three CI jobs). The order to do them in is in section 8.

| Lens | Grade | One-line reason |
|---|---|---|
| Full-stack / Go core | B+ | Storage, engine, events and RPC boundary are correct and tested; status writes are not fenced, check commands inherit the host environment, nothing is retained or compacted, no linter in CI. |
| Security | B | Mediated boundaries are strong and tested; the git chokepoint is unhardened and the security document promises three controls that do not exist. |
| UI / UX | B- | Disciplined Remix 3 code, labelled doubles, 656 passing tests, real CSP; but reconnect re-read is inverted, no virtualisation, light-theme contrast fails everywhere, focus ring vanishes in High Contrast, 13 of 15 dialogs unnamed, e2e not in CI. |
| AI layer | B+ | Cost honesty, data-class guard, deterministic router, quiet sessions and a pre-registered trial are exemplary; a false-REVISE parser, a 4 KB watchdog hash, duplicated brief, and documented-but-unbuilt session policy. |
| Bots / automation | B | Spend and authority are bounded everywhere; the GitHub side has no timeouts, no pagination, no idempotent create, and a rate-limit profile that fails at about ten concurrent PR tasks. |
| Tests and evidence | A- | Claims are proven by real-process tests and numbers recompute exactly; the holes are which suites CI actually runs and a load-sensitive core test. |

## 4. Findings

Severity is the audit's judgement of impact on a shipped Windows product and on the "hard evidence" principle. "Verified" means the lead auditor re-read the cited lines or re-ran the case after a reviewer raised it; every High finding was verified. Line numbers are at `a8d22fb`.

### 4.1 High

**F1. Drydock runs `git` on agent-writable repository state without neutralising hooks, filters or `fsmonitor`, and the promised config-drift check does not exist** (security; verified)
- `internal/git/git.go:103` passes only `-c core.longpaths=true -c core.quotepath=false`; `env()` at `:90-96` hands git the whole app environment. `docs/security.md` s3 (threat T3) states that every git invocation runs with `core.hooksPath` emptied, `fsmonitor` off and drivers disabled, and that `.git/config` and `.git/hooks/*` are hashed at task start with a `security.repo_config_changed` approval on drift. The approval kind exists (`internal/security/action.go:31`) and nothing emits it.
- Why it matters: linked worktrees share the main `.git`. Any agent process that can write there (a non-restricted CLI, a spawned program, a Bash call outside the sandbox) can plant `.git/hooks/post-commit`, `core.hooksPath`, `core.sshCommand` or a `filter.*.clean` plus `.gitattributes`. Drydock's own `Commit`, `SafePoint`, `Diff`, `DiffStat`, `ChangedPaths` and `PatchID` then execute it in the Drydock process on the host. This is also the one path from a sandboxed task back to the host, because `docs/sandbox.md` s7 has Drydock make the commits on the host. The technique is already used elsewhere in the repo (`internal/skills/service.go:511`, `internal/trial/fixture.go:45-47`), and no test asserts it for `internal/git`.
- Fix: in the single git chokepoint and in `PatchID`, add `-c core.hooksPath=<empty dir> -c core.fsmonitor=false`, disable filter and diff drivers, run from a scrubbed environment (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` pointed at an empty file, the allowlist the adapters use plus the `GIT_*` identity variables); implement the snapshot and `repo_config_changed`; add a test that plants a hook and a clean filter and proves neither runs during `Commit`, `SafePoint` and `Diff`.

**F2. Check and preview commands run on the host with Drydock's full, unscrubbed environment** (Go core / security; verified)
- `internal/checks/checks.go:103` (`env := append(os.Environ(), spec.Env...)`) and `internal/checks/preview.go:167`. Agent processes get an allowlisted environment (`internal/agents/claude/adapter.go:461-471`, `proc.ScrubEnv`), but the `verify`, `red`, `green`, `e2e` and `preview` commands, which execute the code the agent just wrote (`npm test`, `go test`, Taskfile targets, `package.json` scripts the agent can rewrite), do not. `docs/security.md` s8 and threat row T9 count the environment scrub as a control.
- Why it matters: an agent that cannot read `GH_TOKEN` or `CLOUDFLARE_API_TOKEN` in its own process writes a test that prints them; the output comes back to the agent as "the latest failure" and is stored under `runs/`. Applies to every project without the opt-in sandbox (the default).
- Fix: one shared environment builder in `proc` used by adapters, checks, preview and the osv-scanner runner (`internal/checks/deps.go:151`), with project-declared check variables as the only additions; record "environment scrubbed" in check evidence.

**F3. The reviewer's verdict is parsed with a regex that cannot contain braces, so a valid `SHIP` with a code snippet in its feedback becomes `REVISE`** (AI; reproduced)
- `internal/pipeline/review.go:41` `jsonObj = \{[^{}]*"verdict"[^{}]*\}`, used by `ParseVerdict` at `:47-69`. Reproduced in this audit with a throwaway test: `{"verdict":"SHIP","feedback":"optional: use map[string]struct{} for the set"}` parses as `REVISE` with the feedback "could not be parsed"; a `REVISE` whose feedback mentions `{}` loses its structured feedback and the worker gets the raw text.
- Why it matters: every false `REVISE` costs a full work and review iteration (median $0.087 per haiku run in the trial, far more on larger models), counts against the five-iteration limit, and is invisible in the ledger because unparseable answers are recorded as `REVISE` (`docs/evals.md` 11.7). Braces in code-review feedback are routine. The pipeline tests have no brace case.
- Fix: scan for balanced JSON objects (a `json.Decoder` started at each `{` preceding `"verdict"`, keep the last that decodes), or stop parsing prose: give the reviewer a `verdict` tool on the workspace MCP server, which already exists, and record the structured verdict the brief asks for (evals.md open question 3).

**F4. The GitHub pull-request flow is not robust to a misbehaving GitHub** (bot; verified at the cited lines)
- No per-call timeout: `internal/git/host/host.go:80` runs `gh api` with the node's context, which has no deadline; `WaitCI.MaxWait` is only checked between polls (`internal/git/host/ci.go:69`). One stalled `gh` call holds the run and its agent slot forever. `docs/github.md:178` promises a per-call timeout.
- Duplicate PRs: `internal/pipeline/prflow.go:119-124` opens the PR, then persists `PRRef`; a crash or a failed `Patch` between the two re-opens on the next attempt (GitHub answers 422, which the flow turns into a question that can never succeed). `docs/github.md:230` promises an idempotent create via `gh pr list --head`; `:315` admits as-built only reuses the stored ref.
- Rate limits: polling every 15 s with two unconditional calls per poll is 480 requests per hour per waiting task against a 5,000 per hour user limit shared with everything else the user does with `gh`; `MaxParallel` allows 16. The ETag support in `GhCLI.Do` has no caller; backoff on a recognised limit is a flat 60 s; a secondary-rate-limit 403 is treated as a plain error that fails the run.
- Transient errors in `pr_feedback` and `ci` (`prflow.go:243-246, 461-464`) fail the whole run after the agents' work was paid for, while `push_pr` and `merge` correctly park on a question (`githubTrouble`).
- Also: list endpoints use `per_page=100` with no pagination (`internal/git/host/github.go:385,399,468,484,497,599`), so a late `CHANGES_REQUESTED` past 100 reviews or a failing check run past 100 is never seen; `replyAddressed` (`prflow.go:146-173`) can double-post review replies after a crash; `FailedLog` reads a whole Actions job log into memory before truncating to 6,000 bytes (`host.go:99-112`).
- Fix: a 60 s timeout and `WaitDelay` inside `GhCLI`; adopt an existing open PR for the branch before `OpenPR` and write `PRRef` in the same transaction as the evidence; pass ETags into `Checks` and back off to `X-RateLimit-Reset` or `Retry-After` with jitter; route `ci` and `pr_feedback` errors through `githubTrouble`; follow `Link` headers; mark replies before posting.

**F5. Workflow run status is written without the lease fence or a compare-and-swap, contrary to `docs/workflow-engine.md:111`, and a finished turn's `done` row is written with the cancellable context** (Go core; verified)
- `internal/workflow/store.go:283` (`commit`) and `:306-312` (`setStatus`) update `workflow_runs.status` by id only; `engine.go:996` (`Cancel`), `:420-423` (`fail`), `:198` and `:1080` likewise. `version` is incremented and never compared. Scenario: Approve and Cancel clicked together; `Resume` sets RUNNING and launches, `Cancel` finds no active driver yet and writes CANCELLED, the new driver's first `commit` overwrites to RUNNING and the cancelled run completes.
- `engine.go:518` writes the success row with the driver context while the failure path at `:524` already uses `context.Background()`. If the app closes between the handler returning and the row write, the finished, paid turn is recorded as cut off and re-run.
- The engine's crash and exactly-once tests are real and pass under the race detector (kill the process, 8 concurrent resumes); they do not cover these two windows.
- Fix: one lease-fenced or CAS status statement (`WHERE id=? AND status NOT IN (terminal)` for `commit`; `AND version=?` for `Cancel`/`Suspend`); `Cancel` takes the lease or refuses; write `done` rows and safe-point refs with a background context under a short timeout.

**F6. The UI re-reads its live queries at the moment the event stream breaks, not when it reconnects, and the room feed loads the whole history unvirtualised** (UI; verified)
- `ui/app/state/eventStore.ts:178-191`: `onError` increments `epoch` before scheduling the retry; `onOpen` (`:169-174`) never does. `ui/app/state/live.ts:273-279` reloads on `epoch`. Every live query fires an RPC while the core is unreachable, records an error, and nothing re-reads after the stream reopens; replay of missed events rescues queries that have a `when` matcher, but `workspace.info` and others have none. The README and `docs/ui.md` s7 promise a re-read on every reconnect; the test "re-pulls after a reconnect" (`messages.test.ts:139-160`) triggers via `onError`.
- `ui/app/screens/room/feed.ts:396-424` pages from seq 0 in pages of 200 until a short page and keeps everything; `room-screen.tsx` renders every row and re-lexes every message's Markdown on every re-render (`ui/markdown.tsx:588`), and re-renders on any project event. `docs/ui.md` 6.4 and 15.4 promise virtualised bottom-anchored lists; there is no virtualisation anywhere in `ui/app` and TanStack Virtual is not a dependency. `ChatFeed` (`chat-feed.ts`) already does newest-first paging and is the model to copy.
- Fix: bump `epoch` in `onOpen` when `attempts > 0` and add a reload-after-open test; page the room newest-first, window the list, memoise Markdown per message.

**F7. Accessibility: light-theme colour tokens fail WCAG AA across every screen, the focus ring disappears in Windows High Contrast, and the details tabs carry an invalid `aria-controls`** (UI; measured by axe on 32 screens and by token arithmetic)
- `ui/app/styles/app.css:65-72`: in the light theme `--success` #2f9e68 is 3.38:1 on white, `--warning` #b7860b 3.27:1, `--info` #1f7ae0 4.27:1, `--text-faint` #8b8f99 3.24:1 (2.94:1 on the sidebar); all are used as 11 to 12 px text (badges, status chips, diff counts, group headings, timestamps). The axe scan found 400 contrast nodes over 32 screens. Dark theme passes for status colours; dark primary-button text on `--accent` is 3.77:1.
- `app.css:186-189` `:focus-visible { outline: none; box-shadow: ... }`: forced-colours mode drops box-shadow, so a Windows-only product has no focus indicator in High Contrast; shadow rings are also clipped by `overflow: hidden` containers (list cards, dialog, main).
- `ui/app/ui/tabs.tsx:84` renders only the active panel while every tab names its panel in `aria-controls` (axe: critical, 31 screens). 13 of 15 dialogs have no accessible name (`ui/app/ui/dialog.tsx:46-47`). The room's `role="log"` live region announces the entire history on open (`room-screen.tsx:248-253`); the Logs panel re-announces its whole buffer on every poll.
- Fix: darken the three light status tokens and `--text-faint` to at least 4.5:1 (about #22805a, #8a6508, #1a63b8, #6b707c), add a `forced-colors` outline, drop `aria-controls` for unrendered panels or render them hidden, `aria-labelledby` the dialog heading in the kit, enable the live region after first load.

**F8. Several AI-layer controls the documents describe as behaviour are not built** (AI; verified by grep and by reading the cited code)
- Context-pressure handoff at 70 % occupancy and same-session continuation (brief s5, `docs/token-control.md` s6): `ContextUsed` is computed by the Claude parser (`internal/agents/claude/parser.go:289`) and read by nothing outside the adapters; no handoff artifact is written on a routed escalation (`internal/router/rulerouter.go:519` sets `handoff: true`; only the watchdog stage-2 path writes one). `docs/model-routing.md` s8 and `docs/claude-best-practices.md` s2 describe both as done.
- Claude `rate_limit_event` is parsed into `ChunkRateLimit` (`parser.go:242`) and consumed by nothing in `core`, `providers` or `router`; `internal/core/turnrouting.go:156-158` hard-codes `Healthy: true, QuotaOK: true` for agent-native models. `docs/model-routing.md` s6 promises that `rejected` marks the model unavailable until `resetsAt`.
- `docs/token-control.md` s1 names ten "proving tests" (for example `TestPrefixByteStable`, `TestOccupancyThresholdTriggersHandoff`); none exists under `internal/`.
- Fix: implement occupancy-driven handoff from `ContextUsed` (the data is already there) and feed rate-limit events into the quota ledger as an `agent:claude` provider window, or move these sentences into the "not built" lists so the documents stay a reliable map.

### 4.2 Medium

**F9. Watchdog hashes only the first 4 KB of a normalised tool result** (AI; verified) — `internal/watchdog/normalize.go:24,42`. A worker that runs `go test ./...` gets outputs whose first 4 KB are stable `ok pkg` lines; a changing failure later in the output leaves the key unchanged, so three runs trip `tool_spin` while the agent makes progress, and `error_echo` fires on "same signature" when only the tail changed. The false-trip rate is unmeasured. Fix: hash head, tail and length, and prefer the structured failing-test list for check output.

**F10. Nothing deletes or compacts events, checkpoints, node executions or raw run output** (Go core; verified) — brief s18 and `docs/packaging.md:80` state 30-day compaction and 90-day deletion; decision P13 and `packaging.md:203` admit no compactor exists. Every stream chunk is persisted twice as events (`internal/workflow/engine.go:614` and `internal/agents/runtime/runtime.go:297,318`) although the chunks are already durable in `runs/<run>/.../stream.jsonl`; `events` has no `project_id` index though the SSE transport filters by it. Growth rate is unmeasured. Fix: publish chunk events without persisting them, write the retention job, add the index, measure.

**F11. One active run per task is enforced only by check-then-act** (Go core) — `internal/core/ops.go:96-120`, `ext_agents.go:424-426`, the 5-second auto-scheduler tick (`internal/pipeline/scheduler.go:200-240`); `workflow_runs(task_id)` is not unique. A double-click or a scheduler race starts two runs on one worktree. Fix: a partial unique index on active runs per task, or a CAS on `tasks.run_id` in the same write transaction.

**F12. `Core.mu` is held across process spawns** (Go core) — `internal/core/core.go:491-507` holds the mutex while `git rev-parse` runs (5-minute timeout on a hung network drive); `ops.go:219-234` holds it while every adapter probes its CLI. One bad repository stalls every project. Fix: look up under the lock, do I/O outside it.

**F13. Unknown or malformed Claude CLI events are silently dropped; the documented drift counter does not exist** (bot; verified) — `internal/agents/claude/parser.go:161-168,251-254`; `docs/connections.md:243` promises `adapter_unknown_events` and local drift detection. A CLI release that renames `result` makes every turn hang until the 20-minute cap with no signal on the Connections page. Fix: count unknown types per session, publish `adapter.drift` past a threshold, treat "no `result` within N minutes after `system/init`" as fatal.

**F14. A hung CLI costs 40 minutes before it is killed** (bot) — `internal/watchdog/policy.go:283-325,371-379`: the 20-minute timer trips stage 1, which interrupts and queues a nudge the hung process never reads; only the second expiry kills it. Fix: when the interrupt is not acknowledged within 5 s, go to stage 2 at once.

**F15. ACP: a requested model or effort the agent does not expose is replaced by the agent's default with a non-fatal warning** (bot) — `internal/agents/acp/session.go:288-323`. A cheap-tier run can silently run on an expensive default. Fix: fatal when a model was requested and is not offered.

**F16. `claude.Adapter.Detect` runs the CLI outside the Process Manager and without a Job Object** (bot) — `internal/agents/claude/adapter.go:125-142` versus `internal/connections/run.go:29-73`, which does it right; `docs/connections.md:19` says every probe uses the Process Manager. ## 6. What is done well, with evidence

- **Storage**: one writer connection with `BEGIN IMMEDIATE`, a `query_only` read pool, WAL, `busy_timeout`, foreign keys on (`internal/storage/storage.go:31-90`); `WriteTx` retries busy with backoff; every migration has a Down step and `schema_test.go:44-96` downgrades, seeds and re-upgrades to prove a data migration.
- **Workflow engine**: lease fencing inside the write transaction (`store.go:233-246`), `INSERT ... ON CONFLICT ... WHERE expires_at < now` lease acquisition, per-attempt `node_executions` rows as the idempotency key, interrupted turns distinguished from failures and gated after two cut-offs. `engine_test.go:213-255` re-executes the test binary and SIGKILLs it; `TestPartialSuperstep` asserts `1:abandoned, 2:done` with effect counters of exactly one; `TestDuplicateResume` fires eight concurrent resumes across two engines and requires exactly one to proceed. All pass with `-race`.
- **Authority**: only `human:` identities complete tasks (`internal/tasks/service.go:518`), decide approvals (`internal/security/approvals.go:299-309`, 21 forged principals tested) and merge (`internal/pipeline/review.go:229-253`, re-checked after a base sync); `run.respond` stamps `By: c.Human()` from configuration, so no transport path lets an agent answer a request.
- **Approvals**: canonical-JSON descriptor with run, node, step and attempt; constant-time hash compare; compare-and-swap `APPROVED -> CONSUMED` once; lineage cancellation on time travel (`internal/security/action.go:45-69`, `approvals.go:432-447`).
- **MCP gateway**: loopback only, per-run 256-bit bearer compared as a SHA-256 in constant time, every `Origin` rejected, allowlist re-checked on `tools/call`, upstream credentials never forwarded on redirect, secret scan and untrusted wrapper with tag neutralisation on every result, deterministic truncation with exact `fetch_range` continuation (`internal/mcp/gateway.go`, `run.go`, `shape.go`, `upstream.go`).
- **Sandbox egress**: resolves names itself and dials only the checked addresses (no re-resolution race), refuses loopback, private, link-local, CGNAT and metadata ranges; the egress container is read-only, capabilities dropped, `no-new-privileges`, with memory and pid limits; the workspace network is internal (`internal/sandbox/egress/egress.go:115-174`, `internal/sandbox/manager.go:209-243`).
- **Secrets**: the Claude child's environment is an allowlist and the enclosing Claude session's socket and token are stripped (`internal/agents/claude/adapter.go:461-507`); outbound prompts and cached completions are gitleaks-scanned; room bodies and briefs are redacted before storage; every log line passes the scrubber and is withheld if scanning fails; the support bundle is scanned a second time after redaction and refused if anything remains. No log statement prints environment, keys or tokens.
- **Cost honesty**: one SQL classification shared by budgets and evals; zero cost means unknown and is never shown as free; CLI cost is labelled as the CLI's estimate; usage is booked as deltas of running totals, a reading established and held by contract tests CLAUDE-USAGE-02/03.
- **Routing and LLM access**: deterministic router with a recorded, explainable decision; fails closed on an unknown ceiling; the data-class guard runs before cache, slot and quota and is never papered over by a fallback; a stream that has emitted is never retried elsewhere.
- **Quiet, bounded agents**: measured first-request token cut from 27,463 to 9,846 (P36); watchdog with stored trip counts; one automatic re-run after an interruption, then a human; responder chains hard-capped at 12 turns and idempotent per trigger; Team Lead answers are strict JSON with unknown fields refused and three interventions per task.
- **UI**: zero violations of the framework rules on sweeps; Markdown through a lexer only with HTML tokens as text and allow-listed link schemes, plus a production CSP without inline script; Monaco and xterm lazy, created in `ref` and disposed with their models; live reads drop stale responses by generation; the chat feed shows the right pattern for paging and streaming; `formatCost` never shows $0 for unreported.
- **Evidence trail**: 316 run-record directories with `run.json`, events, usage, evidence and diff; a pre-registered analysis; hidden checks mutation-tested (65 broken variants for the billing tasks); arms interleaved; rejected results re-run three times to rule out flaky checks; medians and ranges only; honest nulls. Every number in `docs/evals.md` sections 13 and 14 recomputes exactly from the records.
- **CI discipline**: Windows runners on every push, `-count=1`, no retries, paid tests never in `ci.yml`, budget caps and `timeout-minutes` on every job, the starving self-check moved to its own job when it was observed to starve others.

## 7. The evidence culture: what the measured numbers support

What the trials can support: on 23 precise, standard-library Go tickets with haiku, Drydock's worker-plus-reviewer loop costs about 28 % more per run at the median (4 % over all runs) and about a minute more wall time than one plain Claude Code session, with acceptance at the ceiling in both arms (68 of 69 against 66 of 69); putting 87 KB of unrelated skills into every turn costs 1.9 times as much and does not help, while listing them by name costs the same as none; a codebase skill offered only by name was opened in 2 of 6 runs.

What they cannot support, and the ledger mostly says so: any quality difference between arms (2 discordant tasks of 23; the sign test needs at least 6 one-sided discordances for p < 0.05, so the design is underpowered by construction); the value of the review loop (17 runs saw a `REVISE`, but no record keeps the version each review saw); generalisation to other models, languages, Windows, repositories with dependencies, or tickets that leave rules implicit; wall times (12 shards on 4 CPUs). Confounds not separated: B1 had unrestricted Bash while D ran exact check commands; D ran the pre-P36 heavier prompt; B1 carried the user's plugins; cost is the CLI's API-price estimate, not subscription cost. The one n=1 data point in section 12 (a $0.0983 two-turn task) cannot be recomputed from committed records and may include a Sonnet review turn, as the text admits.

Three habits would make the ledger stronger than it already is: keep the version each review saw and run the hidden check on it (the counterfactual the loop's value rests on); gate every printed significance test on the P34 size rule in every tool, not only `Report`; refuse to run a trial from a dirty tree.
