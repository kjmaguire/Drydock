# Workflow engine (`internal/workflow`)

Scope: the in-house orchestration engine from brief section 4. It runs graphs of nodes in supersteps, checkpoints to SQLite after every step, pauses at human request ports, and resumes exactly once after a crash. It has no dependency on Wails or on any agent provider. This document is the contract the code and the acceptance tests follow; where the code diverges, the code's tests win and this file is fixed in the same change.

## 1. Why we do not use Microsoft Agent Framework for Go

Phase 0 (`evidence/phase0/go-probes/maf`) measured its resume behavior with a fan-out of A, B, C into a barrier, B failing:

| Observation | Consequence for Drydock |
|---|---|
| Checkpoint written only after the whole superstep; on failure A and C (already successful) re-ran on resume (counters 2/2) | Per-node `node_executions` rows; completed nodes of an interrupted step are reused, not re-run |
| Two resumes of one checkpoint both ran everything and emitted two outputs | Per-run lease plus request consumption by compare-and-swap |
| No automatic crash recovery; host must rebuild the workflow identically | `Recover()` scans for runs not in a terminal or waiting state and resumes them under a lease; topology hash check |
| Executor-local state is not snapshotted unless hooks are implemented | All node state lives in the checkpoint (shared state map and inboxes); handlers are stateless functions |
| No workflow-level middleware or retry | Our middleware pipeline and retry policy |

We reuse its ideas (supersteps, typed request ports, `Parent`-linked checkpoints, pluggable store), not its code.

## 2. Model

```
Graph{Name, Nodes, Edges, Entry}
Node{ID, Kind(agent_task|check|request|route|subworkflow), Handler, Request?, Sub?}
Edge{From, To, Kind(direct|conditional|fanout|fanin|loop), Cond?, MaxIter?}
Message{From, To, Value(json), Iteration}
```

Graphs are Go values built by builders (`Sequential`, `FanOutFanIn`, `Loop`, `Conditional`, `Debate`); they are never serialized. A checkpoint stores a topology hash (`sha256` of sorted node ids, kinds and edges); resume refuses a graph whose hash differs (`ErrTopologyMismatch`).

Rules enforced at `Graph.Validate()`: unique ids; every edge endpoint exists; at least one entry; fan-in nodes list all expected sources; loop edges carry `MaxIter > 0`; request nodes have a `RequestSpec`; no two nodes share a shared-state key (parallel nodes write only their own namespace `out/<nodeID>`).

## 3. Execution: supersteps

State `RunState` (the serialized checkpoint payload):

```
Step            int                      // number of completed supersteps
Inboxes         map[NodeID][]Message     // messages that will be consumed in step Step+1
Barriers        map[NodeID][]NodeID      // fan-in: sources already delivered
Shared          map[string]json.RawMessage // "out/<node>" results, "in" run input
Pending         map[RequestID]PendingRequest
Waiting         map[NodeID]RequestID     // request nodes parked on a human
LoopCounts      map[EdgeKey]int
Done            map[NodeID]bool          // informational
```

One superstep:
1. **Select** ready nodes: nodes with a non-empty inbox, except fan-in nodes, which are ready only when every declared source has delivered (barrier complete).
2. **Execute** all ready nodes concurrently. Each execution first writes a `node_executions` row `(run_id, node_id, step, attempt)` in `started` state (the idempotency key), then runs `middleware(handler)`. Completed rows from an earlier interrupted attempt of this same step are reused: their recorded output is used and the handler is not called.
3. **Barrier**: wait for all. If any node errored after its retry policy, the step fails and the run goes `FAILED` (there is no `error` edge kind as built). A node error that is a `GateError` (for example the repository's git configuration changed, `security.md` s3) is not a failure: the node raises an approval and runs again once a person answers. Nothing from a failed step is routed.
4. **Route** outputs: for every edge from a finished node, evaluate conditions against the output (`Cond`), enforce loop counters (a loop edge past `MaxIter` routes to the loop's `onExhausted` target or fails the run), and append messages to the next inboxes. Request nodes do not complete: their request is stored in `Pending` and the node is parked in `Waiting`.
5. **Checkpoint** (`kind=step`) in one transaction together with `workflow_runs` status and the new approval rows; the events are published after the transaction commits. The checkpoint's `parent` is the previous checkpoint of this lineage.
6. If no node is ready and `Pending` is non-empty the run becomes `WAITING_HUMAN` and `Run` returns. When the step that raised the requests leaves nothing else to run, its own fenced commit writes `WAITING_HUMAN` with the checkpoint and the approval rows; only a driver that stops at requests without a step of its own (resumed or recovered with requests still open) writes the status separately, retried, and `workflow.status_write_failed` names a write that still failed. (Until 2026-10-13 the step committed `RUNNING` and a second, unchecked write parked the run; had it failed, the run stayed `RUNNING` with no driver and no lease row, which `WatchRecover` skips, until a restart. A Windows CI run of `TestResetLoopsGivesTheLoopItsBudgetAgain` timed out with the run `RUNNING` after the answer; it did not reproduce in 400 local runs, so this is the cause that fits, not a proven one. `TestAStepThatRaisesTheOnlyWorkLeftParksTheRunInItsCommit`.) If nothing is ready and nothing is pending the run is `COMPLETED` with the sink outputs as its result.

Before step 1 of a new run an `entry` checkpoint is written containing the input. Replaying a run from its entry checkpoint with deterministic handlers reproduces the same node sequence (tested).

## 4. Request ports (human in the loop)

A `request` node's handler returns a `RequestSpec{Kind(approval|question|review), Title, Payload, ActionHash?}`. The engine inserts an `approvals` row (`REQUESTED`), stores `PendingRequest` in the checkpoint, parks the node, and emits `workflow.request_raised` and `approval.requested`. Agent tool approvals raised through ACP `session/request_permission` are designed to create the same row, bound to the hash of the exact action; as built (audit 2026-10-16, L29) ACP requests are refused, not asked. **An answer goes where an edge takes it (L14).** The answer to a request that is not retried is the route its node leaves by (`approved`, `rejected`, `answered`). An answer none of the node's edges takes would end the run as if it had finished, with the work it was about left where it was, so `Resume` refuses it (`ErrNoRoute`, naming the answers the step goes on for) and the request stays open; a rejection is the exception, because a step with no edge for it ends the run on purpose (a plan or a spec turned down), and a step with no edges at all is the end of the workflow. A run that was cancelled or ended while an answer was being recorded stays ended: the answer is not recorded (`ErrRunTerminal`), and a paused run comes back only if it is still paused. A run that failed is marked failed with a write that is tried again, so a busy database does not leave it RUNNING for its next owner to run the failing step again.

`Resume(run, Response{RequestID, Decision, Data})`:
1. acquire the run lease (fails with `ErrLeaseHeld` if another instance holds it);
2. in one transaction, CAS the approval `REQUESTED → APPROVED|REJECTED` (a second answer to the same request fails with `ErrRequestConsumed`: duplicate resume proceeds exactly once);
3. write a `response_entry` checkpoint (parent = latest) that records the response, before any node consumes it;
4. deliver the response as the output of the waiting request node, route it, and continue supersteps.

An approval marked `APPROVED` is moved to `CONSUMED` when the action it authorizes actually runs.

**Retry requests (added with budgets, 2026-10-08).** A `RequestSpec` with `Retry: true` parks a node whose work is still owed (the budget gate in front of an agent turn). The pending request keeps the node's inbox; `Resume` restores it instead of routing the answer as the node's output, so the node runs again in the next superstep and reads the human's decision from the `approvals` row (APPROVED is consumed by the run it allows, REJECTED is the node's to act on; the budget gate fails the run). Without `Retry` the answer is the node's output, as before. Test: `TestRetryRequestRerunsTheNodeAfterTheAnswer`.

**Answers, halts and loop resets (added with the Team Lead, 2026-10-09, decision P26).** Three backward-compatible additions, all off by default:
- `RequestSpec.DeliverAnswer` (with `Retry`): `Resume` restores the parked node's inbox and appends the answer `{"decision","data","by","request"}` as one more message, so the node that runs again sees what the human said. The watchdog's pauses use it (section 9): the guidance reaches the agent's next turn, a rejection is the node's to act on. Before this, a watchdog pause on `work` routed the human's answer down `work -> guard` as if it were the work's output, even on a reject.
- `NodeOutput.Halt`: the output is recorded but routed to no edge, not even an unconditional one, so the run completes cleanly after a node stopped the task (a rejected watchdog pause, a human "stop" at a limit).
- `NodeOutput.ResetLoops`: every loop counter of the run is cleared before the output is routed, so the loop budget starts again (a human or the team lead continuing past an iteration limit).
Tests: `TestResetLoopsGivesTheLoopItsBudgetAgain`, `TestHaltEndsTheBranchEvenWithAnUnconditionalEdge`, `TestDeliverAnswerAppendsTheHumanAnswerToTheRestoredInbox`.

## 5. Crash recovery and exactly-once effects

- **Lease**: `run_leases(run_id, owner, expires_at)`; acquired with an atomic `INSERT ... ON CONFLICT DO UPDATE WHERE expires_at < now`; renewed by a heartbeat goroutine at one third of the TTL (default TTL 30 s); released on exit. Owner ids are `hostname:pid:random`.
- **Fencing**: every step commit (and a resume) runs, in its write transaction, `UPDATE run_leases SET expires_at = max(expires_at, now + TTL) WHERE run_id = ? AND owner = ?` and refuses the commit (`ErrLeaseHeld`, the driver stops) when no row matches, i.e. when another owner took the run over. A lease that ran out while its own driver was stalled (a loaded machine, a laptop asleep) but that nobody took is still that driver's: the commit extends it and the run goes on. (Until 2026-10-10 the fence also refused an expired lease of the same owner, which stopped the driver and left the run `RUNNING` with nobody driving it until the next start; seen on the Windows CI runner with the tests' 3-second lease.)
- **Recover()** (called at startup): select runs with status `RUNNING` or `RECOVERING` whose lease is expired (or, only at start, that have no lease row); for each, set `RECOVERING`, acquire the lease, load the latest checkpoint, and continue the loop. Runs in `WAITING_HUMAN`, `PAUSED` or terminal states are untouched. **`WatchRecover`** (started by the core after `Recover`) repeats the expired-lease check every third of the lease TTL (10 s by default) for as long as the app runs, so a run whose dead owner's lease was still valid at start (the app was killed and restarted within the TTL) is taken over as soon as that lease expires. Runs this engine drives and runs with no lease row are never taken by the loop. "Drives" starts with a **claim**: `Start`, `Resume`, `Continue`, `TimeTravel` (and `ResumeFrom`), `Replay`, `ResumeSuspended` and the recovery itself register the run's driver in the engine before they take the lease, and only then write the run and publish its events; the driver goroutine starts after that. (Until 2026-10-12 the driver was registered only when its goroutine started, after those writes. A database stall longer than the lease in between, seen on the Windows CI runner with the e2e harness's 3-second lease, let the watch take a run its own engine had just started or resumed and start a second driver: both ran the same agent turn, and the run could fail on the duplicate `node_executions` row, leaving a plan at `PLANNING` or a task without its review. `TestStartDrivesTheRunOnceWhenTheDatabaseStallsPastTheLease`, `TestResumeDrivesTheRunOnceWhenTheDatabaseStallsPastTheLease`.)
- **Interrupted step**: the checkpoint after step *N* holds the inboxes for step *N+1*. Re-executing step *N+1*: rows in state `done` supply recorded outputs; rows in state `started` (no result) are retried once with `attempt+1` in the same worktree; nodes with no row run normally. This is the partial-superstep guarantee. As built, the retried node gets `NodeInput.Previous` (the earlier attempt number, the path of its partial `stream.jsonl` and its error). The worker's turns read it (decision P39): a retried work turn that follows an earlier work turn of the run starts a fresh session seeded with a handoff artifact (reason `interrupted`: the task, the previous summary, the diff stat, the failing checks), never the partial output; other agent turns start again in a fresh session from the task and the latest feedback. **An agent turn is re-run on its own once** (`AutoRerunsAfterInterruption`, 2026-10-10): when a step of an `agent_task` node has been cut off twice (the app crashed, or was closed while the turn ran: an attempt whose driver is stopped mid-node is now recorded `abandoned`, not `failed`), the node raises an approval request instead of running (gate `interrupted`, `Retry`: "The work turn was cut off 2 times because Drydock stopped while it ran..."), so a turn that keeps being interrupted (an app that crashes during it, a machine that keeps sleeping) is not paid for again at every start. Approved, the turn runs once more; rejected, the run fails with the reason. Checks and other nodes are re-run without asking (they cost no tokens). `TestAnAgentTurnCutOffTwiceWaitsForAHuman` kills a child process twice inside the turn; `TestAnAgentTurnStoppedTwiceByClosingTheAppWaitsForAHuman` closes the engine twice.
- **Side effects** (agent processes, worktrees, commits, merges) are idempotent Go operations keyed by `(run_id, node_id, step, attempt)`; handlers receive the key and must use it (for example the worktree path is derived from the task id, and `git worktree add` is skipped when it already exists). The safe point before an agent turn is recorded under the run's own ref, `refs/drydock/safe/<task>/<run>/<step*100+attempt>` (P123; before, `refs/drydock/safe/<task>/<n>`, which a restart, a fork or a replay of the task at the same step and attempt moved under the earlier run's execution row; `TestRunSafePointsOfTwoRunsDoNotMoveEachOther`).
- **Agent processes die with the app** (Job Object `KILL_ON_JOB_CLOSE`), so re-attaching is never attempted; the worktree and its uncommitted work survive.

## 6. Resume, time travel and replay (decision P123, `timetravel.go`)

Three calls a person makes on a run that is not waiting for them. None rewrites a checkpoint, a node execution or an approval of another run.

- **`Continue(run, by)`: resume a run that stopped without finishing**, in place. It takes a run that is `FAILED`, or `RUNNING`/`RECOVERING` with no live driver (the app was killed and the run's lease has run out: the recovery watch would take it over too, this does it on a person's word). It claims the run and takes its lease as `Resume` does, then in one fenced transaction moves the run to `RUNNING` (a compare-and-swap on the status and latest checkpoint it read; this is the only write that takes a run out of `FAILED`, and only on a person's word) and writes an `entry` checkpoint whose parent is the latest one of the same run, so the timeline shows where it went on from. The driver goes on from that state, which is the last step that committed: the step that failed or was cut off runs again exactly as after a crash (s5): a node of it that finished is reused (its `done` row), a node that failed or was cut off runs with the next attempt number and its `Previous`, and an agent turn cut off twice still asks a person first. What it does **not** do: reset anything. Same run id, so the same budgets, loop counters, safe points and approvals; an approval or a rejection already given is read again by the gate that asked for it (the budget gate, a git configuration gate, the interrupted-turn gate), so a step a person refused fails again without asking twice, and a run that failed for a reason still true (a loop exhausted with nowhere to go) fails again. A run waiting for a person (answer it), paused by a person (`ResumePaused`), still driven (`ErrNotStopped`, `ErrLeaseHeld`), completed or cancelled (`ErrRunTerminal`) is refused. Event `workflow.run_resumed {by, from, reason, checkpoint, step}`.
- **`TimeTravel(checkpoint, by)`: fork a new run from any checkpoint**, with the state as of that checkpoint: inboxes, barriers, loop counters, shared outputs, the run input. Its first checkpoint (`entry`) has `parent = checkpoint.ID`, so `Lineage(run)` draws the branch, and its state carries `Origin{kind: fork, run, checkpoint, step, by}` (copied into every later checkpoint of the fork). Open requests of the copied state are asked afresh: new approval rows of the new run, written in the transaction that creates it, the parked node keeping its inbox (before P123 `ResumeFrom` dropped the inbox and step of a `Retry` request, so a gated node of a fork lost its input, and wrote the requests in a second transaction). The nodes after the checkpoint run again as executions of the new run and are live: a node that changes something outside the run behaves as in any run. What it does **not** do: touch the run it came from (its status included: stopping it is the caller's business), or rewind anything outside the engine, a task's worktree and files above all (brief 13: the engine never resets a worktree on its own). `ResumeFrom(checkpoint)` is `TimeTravel` without a name.
- **`Replay(run, from, by)`: run an ended run's nodes again**, in a new run, from checkpoint `from` of the run's lineage (empty: the lineage's first, the entry with the recorded input), with the recorded inboxes as the nodes' inputs. A run that has not ended is refused (`ErrNotFinished`), a checkpoint outside its history too. It is a branch as above, with `Origin{kind: replay}`. In a replay a node that changes something outside the run (`MetaEffect`, set with `Node.Effect(what)`: metadata, not topology, so marking a node does not change a graph's hash; the pipeline marks `merge` (local and GitHub), `push_pr` and `plancreate`, `TestEveryStepThatChangesSomethingOutsideTheRunIsMarked`) **never runs without a fresh approval of the replay**: either a person's approval that is the node's own input (the answer to a request just before it, given in this run: a merge after its own `approve` request does not ask twice), or the approval request the node raises first (`Retry`, gate `replay`, `actionHash` `replay/<run>/<node>`, "This replay reached merge, which merges the task's branch into its target branch. Approve to run it again, or reject to stop the replay here."). An approval lets one execution through (it is consumed), a node reached again asks again, a rejection ends the replay there (FAILED, the node not run). Requests, budget pauses and every other gate ask afresh, as in any new run. Inside a subworkflow of a replay the nested run is a replay too, and since a subworkflow cannot wait for a person, a marked node there stops it instead of running.
- **Subworkflows** run under an id derived from the parent's execution, `SubRunID(run, node, step, attempt)` = `<run>-<node>-<step>-<attempt>`, so the run explanation finds the nested run of every execution of the node without a column linking them. A subworkflow that parks at a request is now cancelled (its request leaves the inbox) and fails the parent's step with the request's title, instead of waiting forever for an answer nothing would read.

What the task around a run needs (one live run per task, the task's status, the task channel) is the core's: `internal/core/ext_runcontrol.go`, `run.resume`, `run.timeTravel`, `run.replay` (docs/ui.md 6.2).

## 7. Middleware and observers

```go
type NodeHandler func(ctx context.Context, in NodeInput) (NodeOutput, error)
type Middleware  func(next NodeHandler) NodeHandler
```

Order for `agent_task` nodes (outermost first): `Telemetry → Budget → Context → Security → Watchdog → Usage → Retry → handler`. `check` nodes use `Telemetry → Watchdog(OnCheckResult) → Retry → handler`. Middleware implements stream hooks by also implementing `StreamObserver{OnStart, OnChunk, OnEnd, OnError}`; the engine registers it for the node's lifetime.

## 8. Streaming

A handler emits chunks through `in.Emit(Chunk)` while it works and returns the collected value. The engine, per chunk: (1) appends it to `runs/<run>/<node>/<step>-<attempt>/stream.jsonl` (synced on a 100 ms ticker as built), (2) calls observers' `OnChunk`, (3) publishes a `workflow.node_chunk` event (lossy to slow subscribers, never blocking). Downstream nodes receive only the complete value. A crash loses at most the unsynced tail; `node_executions.partial_ref` points at the file so the retry attempt can seed itself from it. Checkpoints hold references, never stream content.

## 9. Watchdog integration

The watchdog (see `token-control.md`) is both a middleware and a `StreamObserver`. It reads `tool_call` / `tool_result` chunks mid-turn and `CheckResult`s at `check` nodes and loop back edges. A `Trip` makes the engine cancel the node's context with `ErrWatchdogTrip{Signal, Stage, Evidence}`; the agent runtime's handler translates stage 1 into "cancel the turn, continue the session with the nudge message" and stage 2 into "write a handoff, return a `RequestSpec` of kind `question` so the task goes to `WAITING_HUMAN`". Engine and watchdog agree only on `Verdict` and `TurnController` (`CancelTurn`, `Send`), both defined in `internal/workflow`.

As wired since 2026-10-09 (decision P26): the core gives the watchdog per-node thresholds (`watchdog.ForNode`: the Iterate Until Verified profile for every turn of an `iterate-until-verified` run and for the work and test-writing turns of the other task workflows, the defaults for spec, design, review and planner turns), a `Handoff` hook that writes the stage-2 artifact into `handoffs` (reason `watchdog`; its id is in the pause payload), and a `Stop` hook. A stage-2 pause is a `Retry` + `DeliverAnswer` question: on the human's answer the node runs again, the watchdog turns the answer into a readable notice for the agent's next turn and resets the trip count (`Watchdog.Reset`); a rejection calls `Stop` (the task is CANCELLED) and halts the run. `Reset` is also called when a human continues past a limit and when a task enters REVIEW. With a team lead on the project (section 13), a stage-1 trip (mid-turn or an error echo) stops the turn and asks the lead; its message restarts the work, its escalation pauses for the human. Without a lead, stage 1 is unchanged.

## 10. Persistence

Tables (migration `0001`): `workflow_runs(id, workflow, status, input_ref, parent_checkpoint_id, topology_hash, version, created_at, updated_at)`, `workflow_checkpoints(id, run_id, workflow, step, kind, parent_id, state, created_at)`, `node_executions(run_id, node_id, step, attempt, status, output, error, partial_ref, safe_point_ref, started_at, finished_at)` with primary key `(run_id, node_id, step, attempt)`, `run_leases(run_id, owner, expires_at)`, `watchdog_trips`. Run status is derived from the latest checkpoint but cached in `workflow_runs.status`. As built: `version` is incremented on every write but not compared; what keeps writers apart is (1) the lease fence inside each step commit's transaction (a driver whose lease another owner took cannot commit) and (2) the rule that a run that has ended stays ended: every status write and step commit is `... WHERE status NOT IN ('COMPLETED','FAILED','CANCELLED')`, and a driver whose commit finds its run ended stops (`ErrRunTerminal`) without recording the step. So a cancel that lands while a resumed driver is starting or finishing a step is never overwritten by RUNNING (`TestACancelledRunIsNeverRevivedByItsDriver`); the one exception is `Continue`, which takes a `FAILED` run back to `RUNNING` on a person's word, by compare-and-swap (s6); `Cancel` also stops a driver of its own engine that started after it looked. A finished node's `done` row is written with a context that outlives the driver's, so a turn that finished as the app closed is reused at the next start instead of being paid for again (`TestATurnThatFinishedAsTheAppClosedIsNotRunAgain`). Starting a task's run is serialized per task in the core, so two starts of one task (a double click, the scheduler racing the person) start one run (`TestTwoStartsOfOneTaskStartOneRun`). State JSON is stored as a BLOB; bulky payloads (outputs over 64 KB) go to `runs/<run>/<node>/step-<N>/output.json` and the row holds the reference.

## 12. As built: Slice 4 templates, spec gate, PlanTeam, parallel execution (`internal/pipeline`, `internal/checks`, `internal/core/ext_agents.go`)

Everything here is added through new files; no engine file changed. The core registers it from the extension `agents-dev`.

**Post-start registration.** Extensions register graphs after `core.Open` has started the engine, while runs may be in flight. `Engine.Register` was already mutex-guarded, but it silently replaces a graph by name, and a replacement with another topology would strand every waiting run (`ErrTopologyMismatch` on resume). `Engine.RegisterNew` (`workflow/register.go`) refuses a replacement whose topology hash differs (`ErrGraphChanged`), accepts the same topology (new handler closures), and is safe against concurrent `Start`/`Resume` (tested under `-race`, including a waiting run resuming after re-registration).

**Templates** (`pipeline/templates.go`; catalog from `template.list`; `task.startTemplate {taskId, template, agents?, scans?}`):

| Template | Graph (`->` direct, `-x->` on a route) | Extra roles |
|---|---|---|
| `iterate-until-verified` | unchanged (`review.go`), started by `task.start` or `task.startTemplate` | none |
| `feature` | prepare -> spec -> speccheck -valid-> **specreview (human)** -approved-> specaccept -> tests -> testscope -ok-> **red** -red-> work -> verify -pass-> finalize -> review -ship-> **approve (human)** -> merge | `pm` required; `tests` falls back to the worker |
| `bug` | prepare -> repro -> testscope -> red -> work -> verify -> finalize -> review -> approve -> merge | `tests` falls back to the worker |
| `security` | prepare -> scan (informational) -> work -> verify -> gate (scan again, blocking) -> finalize -> sreview (security role) -> approve -> merge | `security` required, never the worker |
| `full-stack-saas` | feature, with an optional `design` node (architect; skipped when the team has none) after the spec gate, e2e inside `verify`, and `secscan` -> `preview` between the review and the approval | `pm` required; `tests`, `architect` optional |

Every loop is bounded (5 by default; 3 for spec and test rework) and exhausts into the escalation (section 13): the team lead first when there is one, then a `limit` question whose "continue" resets the loop budget and whose "reject" cancels the task (`abort`). Roles are resolved once, when the run starts (`pipeline.ResolveRoles`: overrides win, then the first team member whose role matches by name, the PM/security/architect never the worker) and are frozen in the run input (`TemplateInput.Roles`), so a resume or a replay uses the same agents. "Templates set defaults, not locks": any role can be overridden per run, `task.assign` stays the way to set the worker and reviewer, and the project settings switch e2e and preview.

**Spec gate.** `spec` is a read-only PM turn (`RunSpec.ReadOnly`: Claude Code runs in its default mode with Edit, Write, MultiEdit, NotebookEdit, Bash and PowerShell denied; other adapters get their plan mode). `speccheck` parses it deterministically (`pipeline.ParseSpec`): at least one criterion, every criterion a complete Given/When/Then (one-line or Gherkin multi-line with And/But), no duplicates; a spec that fails goes back to the PM with the problems and never reaches the human. `specreview` raises a `review` request (payload `phase: "spec"`, the criteria with ids AC1..., the spec text) and moves the task to `WAITING_HUMAN`. Nothing else can run: the graph has no other path to `tests`/`work`, and the test-writing, design and implementation nodes also refuse to start unless the task has `spec_accept` evidence whose `by` is a `human:` identity (two independent locks, both tested; the golden-path test asserts from the agent prompt log that no test-writing or implementation turn exists before the acceptance). `specaccept` accepts only a `human:` identity (an agent identity fails the run), writes the criteria, with their ids, into `tasks.Acceptance`, records `spec_accept` evidence and returns the task to `IN_PROGRESS`. A human reject sends their text to the PM (`specrevise`); the human may also answer with `data.criteria` (Given/When/Then lines) to replace the criteria, and invalid edits go back as feedback instead of being accepted.

**Test first, red then green.** `tests` (or `repro` for a bug) writes tests; `testscope` checks, from `git status`, that only test files changed (by path convention, `pipeline.IsTestPath`) and, for a feature, that every accepted criterion id appears in a changed test (a textual match on `AC1`, the weakest honest form of traceability); `red` runs the project's own `test` command and requires it to FAIL: a pass sends the tests back (3 times, then a `redlimit` question; a human may approve building without red, which leaves no red evidence and therefore no green claim). Evidence: `red_test` (no verdict, the failing names and log), `green_test` (passed) written by `verifyTDD` after the project's checks pass with the same command. Limits stated plainly: a compile error counts as red (Go: `build failed` with no test names), "green" means the same test command now exits 0, not that each previously failing test was matched by name, and the criterion-to-test trace is textual.

**Security template.** The scans are pluggable by name (`pipeline.ScanRegistry`; `TemplateInput.Scans`, default `secrets`, `deps`): a registered name wins, a name that matches a detected project check (`build`, `test`, `lint`, `typecheck`) runs as that check, any other name is recorded as skipped ("not available in this build"), never as a pass. The built-ins use the economics worker's `checks.SecretsSpec` over the whole tree (diff against the empty tree) and `checks.DepsSpec` (skipped when `osv-scanner` is absent). The first scan is informational and its findings go into the worker's prompt (names and locations, never secret values); the second (`gate`) blocks. Skipped and errored checks are evidence without a verdict and show in the room as `skipped`/`error` from the owning tool member. A blocking gate (`gate`, `secscan`) and the verification run (`verify`) on which no check gave a verdict at all do not pass: the node opens a `question` request (payload `gate: "verdict"`, the checks that did not run, a fingerprint of the content) and runs again after the answer: `answered` checks again, `approved` with `{"waive_verdict": true}` goes on without a result this time (only for that content, only from a person, recorded as `waiver` evidence), `rejected` stops the run (`internal/pipeline/verdict.go`, audit 2026-10-16 M28).

**e2e and preview checks** (brief 13a; `checks/e2e.go`, `checks/preview.go`). `e2e` runs the project's own command, in this order: Taskfile target `test:e2e` then `e2e` (when go-task is installed), `package.json` script `test:e2e` then `e2e`, then `npx --no-install playwright test` when a Playwright config exists and `@playwright/test` is already in `node_modules` (Drydock never installs anything). It reads the Playwright JSON report (only a report newer than the run), names failing tests from it, and copies up to 20 screenshots under the run directory so the evidence outlives the worktree (only image files the report names that lie inside the worktree's `test-results` or `playwright-report` folders once links are followed: the report is written by the project's own run, so a path in it is a claim, `checks.screenshotPath`, audit 2026-10-16 L11). Disabled in the project settings, or not defined: a skipped result (`Result.Skipped`, shared with the economics worker's checks), not a pass. `preview` starts the project's preview command under the process manager (setting `preview.command`, else a Taskfile/`package.json` target named `preview`), refuses commands that look like a production deployment (a lexical guard, not a sandbox; the starter's own `preview` script enforces D6), waits for the health URL (setting, or the first address the command prints that is on this computer: `localhost`, `127.0.0.0/8`, `::1`, or the unspecified address a dev server prints for "everywhere", probed as loopback; an address the command prints that names another computer is never visited, and a probe of a local server does not follow a redirect to another computer, `checks.loopbackProbeURL`, L11) and posts the URL as the Preview member. The process belongs to the preview manager, is stopped when the task ends, when the human uses `preview.stop`, and before the `merge` node removes the worktree. Both are off by default and are switched on per project by a human (`projectdev.set`). On demand: `check.e2e {id}`, `preview.start {id}`, `preview.stop {id}`, `preview.list`.

**PlanTeam.** `plan.propose {projectId, goal, requirements?, plannerAgentId?}` starts the `plan-team` workflow: a read-only planner turn (the PM or architect by default), strict validation (`pipeline.ParseProposal`: one JSON object and nothing else, unknown fields refused, keys, roles, templates, dependencies, no cycles, every acceptance a complete Given/When/Then, at most 30 tasks; control and format characters stripped; a reply that fails goes back to the planner twice, then the plan is `FAILED`), then a `review` request listing the proposed tasks. Requirements text is quoted data in the prompt. Nothing is a task until `plan.accept {planId, accept?, edits?}`: the accepted set must be closed under dependencies, edits are re-validated like a planner reply, tasks are created in `BACKLOG` with `DependsOn` and `Template`, assigned by role (the least loaded matching agent and an independent reviewer; unassigned ones are reported), and a retry after a crash reuses the tasks already created. `plan.reject`, `plan.get`, `plan.list`. The plan row (`plans`, migration 00070) keeps the proposal, the created task ids and who decided.

**Parallel execution.** `scheduler.tick {projectId}` (and a loop that runs only for projects with `autoSchedule` on, on task events and a 5 s timer) promotes `BACKLOG` tasks whose dependencies are `COMPLETED` (`tasks.PromoteReady`), then starts `READY` tasks that have a worker and a reviewer, highest priority then oldest first, within `maxParallel` (runs that are executing count; a run parked for a human does not hold an agent) and each provider's free `max_concurrent`, reporting why each skipped task was skipped. A task starts its template (`task.Template`, set by the planner) or the default workflow, each in its own worktree and branch. Admission is best effort; the invariant is enforced at the agent turn: `pipeline.Limiter` is workflow middleware on every `agent_task`, registered outermost with `Engine.UseOutermost` (also in `register.go`) so the time a turn is queued does not count against the watchdog's wall-clock cap, which starts inside the watchdog middleware (and the room responder's gate), which makes the turn wait for a project slot and for `providers.Monitor.Acquire` on the agent's provider, so resumed runs and room replies obey the same limits. Tested: four tasks, limit 2, real worktrees (peak exactly 2, never 3), a provider with `max_concurrent 1` serializing two agents, and the conflicting merge parked as a question by the existing `Merge` node. Merging stays a human action: every template ends at `approve`, and no scheduler code path merges.

**Project settings** (`projectdev.get/set`, stored in `settings` under `devloop:<project>`; human identity only): `maxParallel` (default 2), `autoSchedule` (default off), `respond` (default on), `e2e.{enabled,command,timeoutSec}`, `preview.{enabled,command,url,timeoutSec}`, `ciMode` (the CI gate before a pull request is merged: `required` by default, or `none` when a human declares that the repository has no CI, which records `ciNoneBy` and `ciNoneAt`; docs/github.md section 5).

**Starting a template.** `task.startTemplate` and the scheduler start a task in its template. `task.start` (`Core.StartTask` in `core/ops.go`) now also starts a task that has a template other than `iterate-until-verified` through `StartTemplate`, so the spec gate cannot be skipped; a task with no template starts `iterate-until-verified` (or `iterate-until-verified-pr` in a `pr_flow` project).

**Not built / unverified.** Each template also has a PR variant (`<name>-pr`, `PRSuffix`): in a `pr_flow` project `task.startTemplate` starts it, and the run pushes, opens the PR, waits for CI and merges through GitHub after the human's approval (`github.md`). UI (built since): the task page picks the template and starts it (`task-controls.tsx`), the spec review panel shows the criteria to accept, edit or send back, the Plan screen runs PlanTeam, the Tasks page has the scheduler panel, Project settings holds the per-project settings below, and every run has its graph and timeline page (`ui/app/screens/run`). In the app these flows run on the real agent adapters (Claude Code headless, the ACP CLIs). Real-agent test coverage: real Claude Code (haiku) for the planner, a room reply, the `iterate-until-verified` loop with a real worker and reviewer, and the core's economics loop; the template flows, the spec gate and the scheduler are tested with the scripted stand-in agent (labeled), not with real agents. The starter project's e2e was exercised as far as `playwright test --list` (real Playwright, no browser exists in the sandbox); its full browser run is an opt-in test (`DRYDOCK_RUN_STARTER_E2E=1`). Everything Windows is unproven (P2): process-tree kill of a preview server on Windows, and the Windows path handling of the test-file heuristic, are compiled (`GOOS=windows go vet`) but not run.

## 13. As built: orchestration fixes and the Team Lead (`internal/pipeline`, `internal/watchdog`, `internal/core/ext_lead.go`; decision P26)

**What every turn carries.** A work turn always carries the task: title, description (clipped to 1,500 bytes on a later pass), acceptance criteria, then on a later pass only the latest failure, review feedback or guidance (never the previous session). Guidance from a human (`data.text`, `data.feedback`... or `key: value` lines) or the team lead is rendered as text, never as JSON. The accepted spec without its criteria section (`pipeline.SpecContext`, 4 KB) goes to the test writer, the architect and every implementation pass of the spec-gated templates; the architect's notes (3 KB) to every implementation pass. A task without acceptance criteria asks the worker to state a 1-3 bullet "Definition of done:" first (kept as `definition_of_done` evidence and checked by the reviewer). `Deps.ProjectBrief` (wired by the core's owner) puts a bounded brief (2 KB) into the worker, spec, design, tests and planner prompts; the core also renders it (4 KB) into the generated AGENTS.md through `ctxeng.Engine.Standing`. The planner also sees the open tasks (title and status, at most 40) and the team (name, role, adapter). Reviewers see the diff in full up to 48 KB; beyond that the prompt says the diff is TRUNCATED and lists every changed file with `+added -removed`. A verdict is the JSON object, or a reply that is exactly the word SHIP; anything else is REVISE. The spec gate's second lock (`IsGated`) covers `feature-pr` and `full-stack-saas-pr`.

**Escalation.** Every task workflow (`iterate-until-verified`, `-pr`, `task-pipeline`, all templates and their PR variants) ends its loops in the same sub-graph:

```
<loop exhausted> / review -stuck-> escalate -lead-> resume -> work | spec | tests | sync | approve
                                     └-ask-> limit (question) -approved/answered-> resume
                                                               -rejected-> abort (task CANCELLED, run ends)
```

`escalate` names the trigger (`iteration_limit`, or `repeated_revise` when the reviewer sent near-identical REVISE feedback in 2 consecutive rounds: normalized bigram Jaccard >= 0.8) and asks the team lead; `limit` moves an IN_PROGRESS task to WAITING_HUMAN and carries `LimitPayload` (trigger, origin, evidence, iteration, the lead's view). `resume` accepts only a `human:` answer or a lead decision: `data.action: "stop"` cancels the task; otherwise the task gets 5 more review rounds when its iteration limit was used up, goes back to IN_PROGRESS (unless the work resumes at `sync` or `approve`, which keep VERIFICATION), the run's loop counters reset (`ResetLoops`), the watchdog count resets for a human, and the work resumes where the exhausted loop came from (a spec loop at `spec`, the test scope at `tests`/`repro`, a refused merge at `sync` locally or `approve` on GitHub, otherwise `work`) with the guidance. Changing these graphs changed their topology hashes: a run of the old graphs that is parked at the update cannot be resumed (it fails with `ErrTopologyMismatch`); the old `limit` dead-ended anyway.

**The Team Lead.** An agent whose role is `lead` (also `team lead`, `manager`, `supervisor`) supervises the project's tasks. Drydock decides when it is asked, deterministically: (a) a stage-1 watchdog trip on a task's turn (spin, cap, wall clock, error streak, echo), (b) an iteration limit, (c) repeated REVISE feedback, (d) a RUNNING task with no progress events for `leadStallMinutes` (project dev setting, default 15; the monitor runs every minute and asks once per silence; the lead's own turn on the task is not progress: before 2026-10-13 its session's last events, landing after the stored intervention, started a new silence the lead was asked about again), (e) a READY/BACKLOG task with no worker or reviewer while `autoSchedule` is on (asked once per task). The lead runs one read-only turn (`RunSpec.ReadOnly`, as for the spec turn above; its own purpose and practices, MCP as for any turn, the budget checked first) with a compact digest (task, criteria, trigger and evidence, last tool calls, latest failing check, last two review feedbacks, last final text, diff stat, the team with roles, adapters and open-task load, the bound used so far) and must answer one JSON object `{"action","message","agent"?,"tasks"?,"reason"}`, validated strictly (`ParseLeadDecision`: unknown fields, unknown or wrong agent, a reassignment to itself, the reviewer or the current worker, a split without Given/When/Then criteria...). An invalid answer is retried once with the problems, then becomes an escalation. Actions: `nudge` (the message is the worker's next guidance: at a limit through `resume`, after a watchdog trip as the restarted turn's notice, for a stalled task into the running turn through `Watchdog.Steer`), `reassign` (`AssignTask` to that agent; an independent reviewer is kept or picked; then as a nudge), `split` (1-5 BACKLOG follow-ups, the lead's text quoted as agent-authored; each carries the origin `lead:N` and waits for a person to move it on even under automatic scheduling, at most two steps from a task a person made and 25 unfinished follow-ups per project, audit 2026-10-16 M27; the current task continues with the message as its narrowed scope), `escalate` (the human question carries the message; for a stalled task the running turn is parked on a question), `continue` (nothing more: the default behaviour applies, at a limit the human question). Every intervention is stored (`lead_interventions`, migration 00103), posted in the task channel by the lead and published as `lead.intervened {taskId, trigger, action, reason, interventionId, agent, createdTasks, invalid}`. Bounds: 3 interventions per task and run (then the human, told so in `lead.exhausted`), a turn that failed included (stored with action `failed`, no room post; 2026-10-10: before, a failing lead was asked again at every silence of a stalled run), one supervision turn in flight per task, the lead's own turns never trigger it. What the monitor already asked is read from the stored interventions, so a restart asks neither about the same silence nor about the same unassigned task again (an unassigned task is asked about again once it changes). Without a lead nothing changes. `lead.standup {projectId}` posts a short on track / at risk / blocked status in #general (`lead.standup` event); `lead.interventions {projectId, taskId?}` lists the log; `lead.tick {projectId}` runs the monitor's pass on demand.

**Not verified.** The lead runs on the real agent adapters in the app, but all of it is tested with the scripted stand-in agent (labelled), not with a real lead model: whether a real model keeps to the JSON contract, and how good its decisions are, is unmeasured. Lead turns do not take a parallel-agent slot (they are short and read-only).

## 14. As built: the group-collaboration node (decision P118, `internal/agents/responder/group.go`)

Brief s4's "group collaboration with bounded debate" is a node kind, `group` (`workflow.KindGroup`, `workflow.Group`), whose
handler is built by `responder.GroupNode(id, responder, spec)`: `spec` reads a `Discussion` from the node's input (the room,
the topic, the named agents in speaking order, the bound, default 3 rounds). The node posts the topic as a SYSTEM message
(idempotent per run, node and step, so an attempt run again continues the same discussion) and the discussion is the thread
under it. Each turn is granted by the room's scheduler in sequential mode with the node's own order and bound
(`room.GrantGroupTurn`: the round counter of a sequential room, room-protocol s6 rule 7; a person's message in the thread
starts the count again) and runs as a real, read-only agent turn through the Agent Runtime on its grant, with the reply's
context selection, manifest, budget check (project, agent, task) and model routing, its prompt saying the round, the bound
and the other agents. The discussion ends at the bound, or earlier when every agent in turn passed; the scheduler's bound
resolution then posts the SYSTEM line and either adopts the DECISION an agent proposed (a `[DECISION]` line) as the
candidate or asks a person with a blocking QUESTION (an Inbox item). The node's value is a `DiscussionResult` (thread,
rounds held, the outcome, the decision's id and text or the question's id, the turns) and its route the outcome,
`decision` or `question`, so the next node gets it. A turn that fails, an agent that is not a member of the room (agents do
not join on their own) or fewer than two agents fail the node. The node is not wrapped by the `agent_task` middleware
(watchdog, telemetry, the budget gate): its turns are replies and are guarded as replies are. A promoted `[DECISION]` line no
longer counts as a turn of its own in the round counters (it made the agent look as if it had spoken in the next round).
Tested in the engine against the scripted stand-in agent (`TestAGroupNodeEndsInADecisionCandidateTheNextNodeReceives`,
`TestAGroupNodeThatDoesNotConvergeAsksAPersonAtTheBound`). Not built: a shipped template that uses the node, a UI to start
one, its turns counted against a workflow budget, and early ending on a `SHIP` verdict (it ends on the bound or a round of
passes).
