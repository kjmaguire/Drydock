# Drydock: security design

Scope: this document is the security design for Drydock v1 (Windows-only desktop app that orchestrates real AI coding agent CLIs). It covers the threat model, the explicit statement that a Git worktree is not a sandbox, approval kinds and the action-hash binding, path and symlink guards, command analysis (including an honest Windows PowerShell/cmd strategy, because `mvdan/sh` parses POSIX only), secret scanning with gitleaks, `data_class` enforcement points, untrusted-content rules, provider-terms consent gates (D1 Claude, D2 Antigravity/Gemini), the Windows hardening roadmap, the audit log, and the Cloudflare preview/production agent-side allowlist (D6). Section numbers cited as "brief §N" refer to `docs/brief.md`; D1-D14 and P1-P6 refer to `docs/decisions.md`; evidence is cited to `docs/phase0.md` and `docs/phase0/*.md`. Nothing here is implemented yet; every Windows behavior is unproven (P2). Statements not backed by the brief, decisions or appendices are marked **design assumption** or **unverified**.

## 1. Principles

1. All AI-generated actions and all retrieved content are untrusted (brief §16). Retrieved content is data, never instructions, and can never change permissions or answer approvals.
2. Be honest about enforcement strength. Drydock hard-enforces only what Drydock itself executes or mediates. Everything an agent CLI does inside its own process is **cooperative** (we ask, the CLI may comply) unless an OS-level control (section 14) is in place. The UI must never imply a sandbox that does not exist.
3. Fail closed: unparseable command, unresolvable path, unknown provider policy, missing consent, scanner error: deny or ask, never allow.
4. No cloud component and no automatic upload of source (brief §0). Telemetry export is optional, off by default and never carries prompts, code, tool output or secrets (brief §10, D12).
5. Humans answer approvals. No message from an agent, tool, MCP server, GitHub, or integration can produce an `APPROVAL`.

## 2. Threat model

Assets: user source code and uncommitted work; credentials (CLI logins, API keys, Credential Manager entries, `gh` token); Drydock's SQLite database and raw run output; the user's machine and other repositories; production infrastructure (Cloudflare, GitHub); the user's standing with vendors (account suspension, D1/D2).

Actors: (a) the user (trusted); (b) agent CLIs (semi-trusted code running with the user's OS permissions, steered by untrusted model output); (c) model providers (see `data_class`); (d) content authors reachable through repo files, docs, MCP servers, GitHub issues/PR comments, Linear/Notion/Sentry/Aikido items, web docs (untrusted); (e) other agents in the room (untrusted for instruction purposes); (f) supply chain (npm ACP bridges, MCP servers, skills, dependencies).

## 3. A worktree is not a sandbox

Statement (shown in onboarding, in the Agent Inspector and in the approval dialog footer): **A Git worktree isolates branches and files for review. It does not restrict what an agent process can read, write, execute or send over the network. Agents run with your Windows user's permissions.**

Concretely, in v1 an agent process can, if it decides or is tricked to: read and write any file the user can (other repositories, `%USERPROFILE%\.ssh`, `%USERPROFILE%\.claude\.credentials.json`, Codex `auth.json`, Gemini `oauth_creds.json`, OpenCode `auth.json`; locations from agent-clis §13); read and write Drydock's own database and raw run output; read Credential Manager entries of the same user; spawn any program; make arbitrary network requests; modify other worktrees of the same repository.

Git-specific consequences: linked worktrees share the main repository's `.git` directory, so hooks (`.git/hooks`), `.git/config` (including `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, filter/diff/merge drivers, includes) and refs are writable from any worktree. Drydock therefore:
1. **No hooks, no fsmonitor, no diff drivers in its own git calls (built, `internal/git/git.go`).** Every `git` invocation Drydock makes runs with `-c core.hooksPath=<an empty directory of Drydock's own> -c core.fsmonitor=false`, and `diff`/`show`/`log` with `--no-ext-diff --no-textconv`. The user's own hooks do not run in Drydock's safe points and commits either (brief §13). The environment drops every inherited `GIT_*` variable except how the user reaches remotes (`GIT_SSH*`, `GIT_ASKPASS`, `GIT_SSL_*`, `GIT_PROXY_COMMAND`, `GIT_EXEC_PATH`) and which of the user's own configuration files git reads (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`; the `-c` settings above override every file), so an inherited `GIT_DIR`, `GIT_CONFIG_COUNT`/`KEY`/`VALUE`, `GIT_CONFIG_PARAMETERS` or `GIT_EXTERNAL_DIFF` cannot redirect or run anything. `Status` confirms a worktree-only modification against the content (`git diff --name-only`): under `core.autocrlf`, the Git for Windows default, a file written back with LF and the same text differs only in size, which `git status` alone reports as a change. A repository inside a WSL distro (P41) runs these same calls with the distro's own git (`wsl.GitRunner` behind the one chokepoint, `git.Runner`), with the same `-c` settings and only Drydock's own `GIT_*` values; a Windows git that reaches a distro path anyway gets `-c safe.directory=<exactly that path>` on its own command line, and the person's global configuration is never changed.
2. **Configuration guard (built, `internal/git/guard.go`, `internal/core/gitguard.go`).** Filter, merge and credential programs, `sshCommand`, includes and the rest cannot be switched off one by one, so Drydock keeps the repository's configuration as a person last trusted it: one hash per config key (the repository's `config`, `config.worktree` and every worktree's `config.worktree`, parsed by git itself), per hook file and for `info/attributes`, never a value. The trusted state is recorded when the person gives the project its repository (creating the project with it, attaching it or importing onto it) and kept in settings across restarts; recorded at the repository's first use instead (as before 2026-10-13), a setting planted in between was taken as trusted unseen (`TestASettingPlantedBeforeTheFirstUseIsNotTrusted`; found by the Windows CI run of `ui/e2e/round15.spec.ts`). A git call that could run a configured program (anything but `rev-parse`, `cat-file`, `merge-base`, `rev-list`, `show-ref`, `for-each-ref`, `symbolic-ref`, `patch-id`) refuses to start while the state differs (`git.ConfigChangedError`, naming the changed keys). In a run the refusal becomes an approval request with the gate `repo_config_changed` (`workflow.GateError`); approving trusts exactly the state the person was shown (if it changed again since, the node asks again about the newer change), rejecting stops the run. Outside a run `project.gitConfig` shows the changed items and `project.trustGitConfig` trusts them by fingerprint. Git's own branch bookkeeping (`branch.<name>.*`, written by `push --set-upstream` and removed by `branch -D`) is not counted, except `mergeOptions`. Proven by `internal/git/guard_test.go` (a planted hook, `core.hooksPath`, `core.fsmonitor` and a clean filter never run in Drydock's commit, safe point, diff, status and merge, while a plain `git commit` does run them; a restart keeps the trusted state; inherited `GIT_*` variables are ignored) and `internal/core/gitguard_test.go` (a filter planted from a task's worktree stops the merge on an approval that names the key and not its value; approving lets it through). Run on the Windows CI runner with Git for Windows.
2a. **Calls are pinned to their repository; nested repositories are opaque (built, `internal/git/pin.go`; audit 2026-10-16, C1).** Git decides which repository a call belongs to from the folder it starts in, and in a task's worktree that folder is the agent's to write. A `.git` file that says `gitdir: ./.x` sends git to a configuration the agent wrote (a `filter.x.clean` there runs on the host, outside the sandbox and without the guard noticing, because the guard watches the common git directory), and a repository planted inside the tree (or a submodule) is asked whether it is modified by a git started in it, with its own configuration. So: (1) every call in a worktree runs with `GIT_DIR=<common>/worktrees/<name>` (the private directory git registered for it, in `<common>/worktrees/*/gitdir`, which the worktree cannot change) and `GIT_WORK_TREE=<worktree>`; the worktree's `.git` file is never read. A folder that is neither the main working tree nor a registered worktree is refused (`git.ErrNotAWorktree`). (2) `status` and `diff` run with `--ignore-submodules=all` (a command-line flag beats a `.gitmodules` `ignore = none`) and every call with `diff.ignoreSubmodules=all`, `status.submoduleSummary=false`, `submodule.recurse=false`. (3) `git add -A` leaves nested repositories out with `:(exclude,literal)` pathspecs (staging a path that is already a gitlink asks the nested repository too), so Drydock neither stages nor shows what is inside one, and `Status` does not count an embedded repository as work. (4) `DeleteWorktree` refuses a worktree that holds a nested repository unless forced (git's own rule for submodules), puts the `.git` file back to what git wrote before `git worktree remove --force` (git re-reads that file and runs a status from it), and does its own clean check through the pinned `Status`. (5) The tools Drydock starts that run git themselves (the security scan's Opengrep) get `GIT_CONFIG_COUNT/KEY/VALUE` settings for an empty hooks directory, `core.fsmonitor=false` and `diff.ignoreSubmodules=all` (`proc.GitConfigEnv`); command-line configuration outranks every file. Proven by `internal/git/pin_test.go`: a redirected `.git` file and an embedded repository (untracked, and recorded as a gitlink, with a `.gitmodules` `ignore = none`) each carry a clean filter that writes a marker; the marker never appears across every operation of the package, and the same planted tree under a plain git call does write it.
2b. **Configuration an agent CLI finds in its working folder (built, `internal/agents/repoconfig.go`, `internal/core/agentconfig.go`; audit 2026-10-16, M3).** Claude Code is started so that it ignores the folder's settings. The other CLIs have no such switch, and Gemini CLI refuses to start without a person at a terminal in a folder it does not trust, while in one it trusts it loads the folder's settings, hooks, MCP servers, commands, extensions, skills, policies and `.env` files (read in its 0.64.0 source). A manifest therefore lists the paths its CLI acts on (`repo_config`), and the runtime does not start that CLI in a folder that has any of them (a link out of the folder counts as found) unless a person trusted the fingerprint of exactly those files: names, kinds, sizes and content digests, so a changed file is a different fingerprint. The refusal is an `agent.failed` event with the files and the fingerprint, a notice and an inbox item in the project's alerts; `project.agentConfig` shows what each CLI would find in the repository and in the worktrees of unfinished tasks, and `project.trustAgentConfig` (a human only, audited) trusts what was shown. An agent that writes such a file in its own worktree is stopped at its next start. **Not verified:** the lists for OpenCode, Codex and Cline are from their documentation and were not run; nothing was run against a real Gemini CLI (no key was used).
3. Treats `.gitattributes`, `.gitmodules`, `.vscode/*`, `.husky/*`, npm lifecycle scripts, Playwright and Wrangler configs as code-execution surfaces: they only run inside `check` nodes whose commands a human configured (never inside commands an agent composed without analysis). A `.gitattributes` naming a driver defined only in the user's own (global or system) configuration runs that driver; the guard covers drivers defined in the repository.

**The per-task sandbox changes this for task work** (P30, [`sandbox.md`](sandbox.md)): in a project with the sandbox switched on, a Claude Code worker runs in Claude Code's restricted mode (no tool that runs commands or code; file tools confined to the worktree; writes to `.claude/` settings and `.git/` refused) and every command it runs, and every check, runs in a container made for the task that sees only the worktree and reaches only the project's network allowlist. The statement above still holds for agents that are not in a sandboxed project, for room replies and reviews (read-only, on the machine), for other CLIs (which cannot work in a sandboxed project yet), and for the container engine itself, which is not a boundary against an engine or kernel vulnerability.

Instruction-file poisoning: Drydock owns `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.goosehints` in each worktree (brief §9). An agent can edit them. Human edits are offered back as memory updates (brief §9), but diffs to these files authored by an agent run are never auto-merged into project memory or standing instructions; they appear as a proposed memory change that only a human can accept. Generated files are regenerated from memory on the next run, which bounds persistence.

## 4. Enforcement tiers

| Surface | Control | Strength in v1 |
|---|---|---|
| Git operations, worktree lifecycle, file deletion initiated by Drydock, merge, push, `gh` calls | Drydock executes; approval consume + path guard | Hard |
| Agent file access via ACP `fs/read_text_file`, `fs/write_text_file` (our `acp.Client`) | Path guard in the client implementation (the SDK example client only checks "absolute path", go-platform §5) | Hard, only if the agent uses ACP fs methods |
| ACP `session/request_permission` (**not built as an approval path**: Drydock installs no permission handler for ACP agents, so every request is answered with the agent's own reject option, or cancelled when it offers none, and is never approved; a person cannot approve one yet, audit 2026-10-16, L29); OpenCode/Antigravity ACP or deny modes (D11). Claude `--permission-prompt-tool mcp__drydock__permission_prompt` for a Claude worker outside a sandboxed project (decision P40, s5 "Claude permission prompts"): every tool use its permission mode and allow rules do not cover goes to the gateway's `permission_prompt` tool, the analyzer, and a person's hashed approval. Not given to read-only sessions (reviewers, room replies, the planner, the lead: their mode and deny list decide), to chats, or to sandboxed workers (restricted mode; the container is the boundary) | Analyzer + approval, answer chosen by human | Cooperative: gates only what the CLI chooses to ask about. What the CLI's own mode or allow rules permit (edits in the working folder under `acceptEdits`, the check commands of `checks.WorkerRules`, `mcp__drydock__*`) never reaches Drydock, and a mode that skips prompts (`bypassPermissions`) skips it entirely |
| Agent shell/exec tools | CLI permission mode set conservatively; analyzer on requests; PATH shims for sensitive tools (s13) | Cooperative |
| MCP calls via the per-run Gateway | Per-role allowlist, shaping, secret scan, untrusted marking, audit | Hard for tools reached through the Gateway; the CLI may also have its own MCP config, so adapters use strict configs (`--strict-mcp-config` for Claude, agent-clis §1) |
| Provider routing | Router + Context Engine + LLMClient + config writer | Hard for Drydock-originated calls |
| Process lifetime | Job Object KILL_ON_JOB_CLOSE (D7) | Hard (unproven on Windows, P2) |
| Credential exposure | Env builder allowlist; no tokens in env except the provider key an agent needs | Hard for env; files under the user profile remain readable |
| Commands of task work in a sandboxed project (P30) | Claude Code `--restricted` removes its command tools; commands and checks run in a per-task container through the Gateway's `sandbox_*` tools; egress proxy with an allowlist | Hard for what the container can reach (the engine's isolation, not proven on Windows); the restriction of Claude Code's own tools is the CLI's (contract CLAUDE-RESTRICTED-01/02) |

Adapters set the most restrictive permission mode that still lets the task proceed and surface denials to the human rather than silently widening. Known: OpenCode headless `run` auto-rejects unanswered permissions unless `--auto`, and Antigravity `-p` soft-denies (D11); Drydock never passes `--auto`, `--dangerously-skip-permissions`, `--yolo`, `--dangerously-bypass-approvals-and-sandbox`, or `bypassPermissions` unless the user explicitly selects that mode for an agent, which requires an `approval` of kind `permission_mode_escalation` and a persistent red badge.

## 5. Approvals

States (brief §12): `REQUESTED -> APPROVED | REJECTED | EXPIRED | CANCELLED`, `APPROVED -> CONSUMED`. Requests are workflow request ports (brief §4); the run waits in `WAITING_HUMAN`.

| Kind | Trigger (examples) | Default policy | Notes |
|---|---|---|---|
| `fs_delete` | Delete files, delete a worktree (dirty worktrees never deleted without it, brief §13) | Ask | Hash includes resolved targets with file identity |
| `fs_outside_worktree` | Read/write outside the worktree boundary | Deny, ask to grant once | Path guard result (s6) |
| `git_force_push`, `git_branch_delete` | `push --force`/`+refspec`, `branch -D`, remote branch delete | Ask, never remembered | Hash includes remote ref, old and new object ids |
| `git_push` | Push of a task branch | Ask once per branch/target (**design assumption**) | `pr_flow`, brief §13b |
| `deploy` | Any deploy command | Agent processes: **hard deny** for production (D6); human-initiated deploy flows only outside agent processes | Reconciles brief §16 ("approval for deploying") with D6 and brief §13a ("production deployment is never a check") |
| `db_migration` | Remote/production migrations (`d1 migrations apply --remote`-style) | Ask; local-state migrations in the worktree do not need it | Wrangler local state is per worktree (tooling §1e) |
| `secrets_access` | Creating/reading secrets, `wrangler secret ...`, reading credential files | Ask | Reading CLI credential files is always denied for agents we mediate |
| `infra_change` | Cloud/IaC changes | Ask | |
| `shell_destructive` | Analyzer class `destructive` | Ask | s7 |
| `shell_unanalyzable` | Analyzer confidence `opaque` | Ask, never auto-allowed by stored rules | s7 |
| `mcp_write_tool` / `integration_write` | State-changing MCP tool; outbound write to Linear/Notion/Sentry/Aikido/GitHub | Ask by default (brief §11) | Content derived from untrusted input is flagged in the dialog |
| `permission_mode_escalation` | Switching an agent to bypass/yolo style modes | Ask, persistent badge | |
| `repo_config_changed` | Hook/config drift (s3) | Ask | |

Merge is a human action (brief §13), not an approval an agent can request. `review` and `question` requests are different request types and carry no execution authority.

**Action hash.** An approval is bound to a canonical description of the exact action, not to prose.

```go
type ActionDescriptor struct {
    V        int      // descriptor schema version
    Kind     string   // approval kind
    Project  string
    TaskID   string
    RunID, NodeID string; Step, Attempt int // same tuple as the idempotency key (brief §4)
    AgentID, WorktreeID string
    Cwd      string   // canonical resolved path
    Tool     string   // e.g. "shell", "git", "fs.delete", "mcp:<server>/<tool>"
    Shell    string   // bash|powershell|cmd|none
    Program  string; Argv []string // normalized first program and its arguments when parsed
    Command  string   // exact text as executed
    ArgvDigest string // digest of CommandReport invocations (s7)
    Targets  []Target // flat struct: path + volume serial + file index, and remote + ref + oldOID + newOID; sorted before hashing
    EnvKeys  []string // names only, never values; EnvDigest is the SHA-256 of the sorted names
}
// ActionHash = hex(SHA-256(canonicalJSON(descriptor))); canonicalJSON = sorted keys, UTF-8, no insignificant whitespace (own implementation).
type Approvals interface {
    Request(ctx, a ActionDescriptor, reason string, opts ...RequestOption) (ApprovalID, error) // WithTTL overrides the default lifetime
    Decide(ctx, id ApprovalID, d Decision, by string) error // by must be "human:<name>", supplied by the UI service layer; every other author is refused and audited
    Consume(ctx, id ApprovalID, actual ActionDescriptor) error // recompute hash from the real operation; constant-time compare; CAS APPROVED->CONSUMED, single use
}
```

Rules: (1) The executor of the action recomputes the descriptor from what it is about to do and calls `Consume`; mismatch returns `ErrHashMismatch` and emits `approval.mismatch`. (2) Single use: `CONSUMED` is terminal; receipts are idempotent by `(scope, receipt_id)` (brief §18), so a crash between consume and effect cannot double-execute (the node idempotency key `(run_id, node_id, step, attempt)` is part of the descriptor). (3) Lineage: because the descriptor contains run, node, step and attempt, an approval granted on one checkpoint lineage cannot be consumed by a time-travel branch (brief §4); branching cancels outstanding approvals (`CANCELLED`). (4) Expiry: default 30 minutes (**design assumption**), configurable; `EXPIRED` is automatic. (5) The dialog renders the canonical action (resolved paths, exact command, refs and object ids), never the agent's description. (6) Stored allow rules ("always allow") match on the normalized form (program + argv pattern + path scope), never on raw strings, and are not offered for `git_force_push`, `deploy`, `secrets_access`, `shell_unanalyzable`. (7) Only the UI service layer can call `Decide`; the room accepts `APPROVAL` messages only from that layer (room-protocol s5); the Gateway and adapters have no code path to it.

Implementation (`internal/security`, migration `00030`): the service owns approvals with `run_id ''`; it stores them in the existing `approvals` table (`kind='approval'`, security kind in `action_kind`, plus `expires_at`). Workflow-bound rows are answered by the workflow engine's `Resume` (which should call `RequireHuman` on its `By`); `Consume` works for both because the executor always proves its action. Approving restarts the lifetime so the executor has a full window; `Decide`/`Consume` enforce expiry lazily and `ExpireDue` sweeps. Events: `approval.requested|approved|rejected|consumed|expired|cancelled|mismatch|reuse_denied|decide_denied` (the engine's names `approval.approved|rejected` are kept rather than `approval.decided`). The stored payload is a display copy with secrets redacted; the hash is of the exact action. Receipt idempotency (brief §18) is not implemented here.

**Binding to agent-native permission requests (design; not built, audit 2026-10-16, L29: as built, `acp.RejectOnce` answers every ACP request, `manifests.Options.Permission` is not set, and an ACP agent that asks before each tool call can therefore do nothing that needs asking).** ACP `RequestPermission` returns an option choice and carries the tool call kind and `rawInput`, so hashing and binding is feasible (phase0 item 13, Partial). Flow: request arrives, analyzer runs, descriptor built from `toolCall`, approval created, human decides, we answer with the `allow_once`/`reject_once` option kinds only (the demo agent offers these, go-platform §5; real agents unverified). After `allow_once` the CLI executes by itself, so the matching `tool_call_update` is compared with the descriptor; a mismatch emits `approval.mismatch` and pauses the run. Whether agent permission modes skip the request entirely is **unverified** (needs logged-in runs, phase0 s7 item 8).

**Claude permission prompts (as built, decision P40).** A Claude worker turn outside a sandboxed project (`pipeline.prepareWorker` sets `RunSpec.PermissionPrompts`) is offered the gateway's `permission_prompt` tool (`core.offerPermissionPrompts`; only a policy entry naming the tool offers it, never a glob) and started with `--permission-prompt-tool mcp__drydock__permission_prompt` (`claude.argsWith`; never for a read-only or sandboxed spec) and `MCP_TOOL_TIMEOUT` of the approval lifetime plus 5 minutes. Flow:

1. Claude Code, in its headless turn, meets a tool use its mode and allow rules do not cover and calls the tool with `{"tool_name", "input", "tool_use_id"}`. The gateway (`internal/mcp/permission.go`) refuses a malformed request without asking anyone and hands the rest to the Core's `PermissionPrompter`.
2. `security.ClassifyToolRequest` runs it through the analyzer. Shell tools (`Bash` as bash, `PowerShell` as PowerShell) go through the command analyzer and the s7 decision table with the worktree as root: **allowed by rule** when the table allows it (fully parsed, read-only or writing inside the worktree, or a stored rule; no project stores rules or CEL restrictions in this build, so the table alone decides); `exec_code`, which s7 allows only when the CLI's own mode permits, is asked, because the request is the CLI saying its mode did not; a hard-deny hit (credential files, production deploys, ...) is **denied** with the reasons. File tools (`Read`, `Glob`, `Grep`, `LS`, `NotebookRead`, `Write`, `Edit`, `MultiEdit`, `NotebookEdit`) go through the path guard: inside the worktree is allowed, a write into `.git` is asked (`agent_tool`), a known CLI credential file is denied, secret material is asked (`secrets_access`) and a path outside the worktree is asked (`fs_outside_worktree`). Every other tool (web fetch, other MCP servers' tools, subagents) is asked (`agent_tool`). A request about the permission tool itself is denied.
3. Anything asked becomes a security-service approval (`security.PermissionGate`): the descriptor's `Tool` is `claude:<tool>`, `Command` the command of a shell tool or the canonical JSON input (display capped at 4,000 bytes), `ArgvDigest` the SHA-256 of the canonical `{"tool", "input"}` (so the hash covers the whole input, whatever the display shows), plus project, task, agent run (`arun_...`) and agent. The title starts `Permission request: <tool>: ...`; the stored copy is redacted (s8). It shows in Needs you (linked to the task) and on the task page as a pending request of the run with gate `permission_prompt` (the tool, the input, the kind, why, the expiry), answered with **Allow once** or **Refuse**. `run.respond` (`core.Respond`) routes such a request id to `Approvals.Decide` with the human principal after checking it belongs to the run's task; nothing else can decide it, and an agent principal is refused (rule 7).
4. The tool call waits in the CLI meanwhile (polling the row). Approved: the descriptor is computed again from the request being answered and consumed once (rule 1); only then the answer is `{"behavior":"allow","updatedInput":<the exact input>}`. Rejected, expired (the default 30-minute lifetime: **timed out**), withdrawn, or the run ended (the gateway's `EndRun` ends the wait and the open approval is cancelled): `{"behavior":"deny","message":...}` with a plain reason for the agent. An approval covers one call: an identical second request needs a second approval, and a different input never matches the hash.
5. Every decision is recorded as `permission.decided` (event and audit log: tool, outcome `allowed_by_rule|approved|rejected|denied|timed_out|cancelled`, kind, approval id, the input's digest, never the input) besides the approval's own events and the gateway's `mcp.call` (args hash only).

Why not a workflow request port (brief §4): the CLI's tool call is in flight, and a workflow request ends the node (the turn) and resumes it later; the approval is tied to the run through its task and the agent run in the hash instead. Limits: the model can see `mcp__drydock__permission_prompt` among its tools and call it itself; such a call only raises a request a person sees, and its answer grants nothing, because Claude Code reads permission only from its own prompt and each approval is single use and bound to one input. The request and answer shapes were read from the CLI's code (2.1.296) and the Agent SDK's types, not observed in a live turn; contract CLAUDE-PERMPROMPT-01 (paid) is that observation, and whether `MCP_TOOL_TIMEOUT` bounds this call, as it does other MCP calls, is unverified.

## 6. Path and symlink guards

File `internal/security/pathguard.go`. Every Drydock-mediated file operation and every path extracted by the analyzer goes through one function.

```go
func (g Guard) Resolve(root, candidate string) (string, error) // cleaned absolute path, or *PathError wrapping ErrPathEscape, ErrSymlinkEscape, ErrPathDevice, ErrPathUNC, ...
```

Implemented in v1: the pure-string rules (steps 1-6, 9 and Windows case-insensitive comparison) run on any host; the filesystem step resolves symlinks and junctions with `EvalSymlinks` on the deepest existing ancestor and fails closed on dangling or looping links. Handle-based resolution (`GetFinalPathNameByHandle`), file identity and the open-then-reverify step (7, 8, 10) remain the target design and are unproven (P2). 8.3 aliases are detected by pattern and compared with `GetLongPathName` (Windows build only).

Algorithm (design assumption; to be proven on Windows with a fixture suite, P1/P2): (1) reject NUL, reject empty; (2) reject device namespaces and non-drive prefixes unless explicitly allowed: `\\.\`, `\\?\GLOBALROOT`, UNC paths (`\\host\share`) are denied by default (Claude docs note UNC symlink targets for instructions are not followed, agent-clis §13); (3) reject reserved device names (CON, NUL, COM1..) and trailing dot/space segments; (4) reject alternate data streams (`name:stream`) for writes; (5) join relative paths onto the worktree root, never onto the process cwd; reject drive-relative `C:foo`; (6) lexically clean `..`; (7) open the deepest existing ancestor and resolve the **final path from the open handle** (`GetFinalPathNameByHandle`), not `EvalSymlinks` on a string, so junctions, symlinks and mount points are followed exactly as the OS would; compare with the root's final path case-insensitively using Windows volume-serial + file-index identity for the root; (8) if any component is a reparse point whose target leaves the root: `ViaReparse=true, InsideRoot=false` and the operation is denied or escalated to `fs_outside_worktree`; (9) 8.3 short names are expanded by step 7; (10) for create/write, validate the parent, open with `FILE_FLAG_OPEN_REPARSE_POINT` semantics and re-verify after open to narrow TOCTOU (the residual race against a hostile concurrent process is acknowledged: this is why the guard is not a sandbox).

**WSL (built, decision P41, `internal/security/pathguard_wsl.go`).** A Claude Code agent running inside a WSL distro names Linux paths. `Guard.ResolveWSL(paths, root, candidate)` maps the candidate into the distro (a Windows path an interop program used, such as `C:\x`, becomes `/mnt/c/x` under the distro's own mount root, never an assumed `/mnt`; `..` stops at the drive root as it does on Windows, so `D:\..\mnt\d\wt` is `/mnt/d/mnt/d/wt`, never `/mnt/d/wt`, and `..` in a `\\wsl.localhost\<distro>\` path stops at the distro's `/`), checks it against the worktree's Linux location with POSIX rules (case-sensitive, `/` only, lexical), and returns the **real location on Windows**: a drive path (`/mnt/d/src/wt/x` is `D:\src\wt\x`), checked again by the Windows guard on that drive so a junction or symlink leaving the worktree is caught, or the distro's own file (`\\wsl.localhost\<distro>\home\k\...`). A home-relative path (`~`), another distro's files and network shares are refused. Residual: inside the distro's own disk the check is lexical, because Linux symlinks are not reliably resolvable through `\\wsl.localhost` from Windows, so a symlink inside a distro worktree that points out of it is not caught (the worktree is not a sandbox, s3). Proven by `TestResolveWSLMapsMountedDrivesAndDistroPathsToTheirRealLocations`, `TestToLinuxKeepsDotDotInsideTheDriveRoot` and `TestPermissionRequestsOfAWSLAgentAreCheckedInTheDistrosTerms`.

Protected paths regardless of root: `.git` internals for writes by agents (hooks, config), `<app data>` (DB, runs), generated instruction files for non-owner writes (agent edits allowed but flagged, s3), credential files of known CLIs (never readable through mediated tools). Worktree deletion: refuse if dirty, refuse if the target resolves outside `<app data>/worktrees`, refuse if any reparse point inside leads outside (do not recurse through junctions; remove the link itself). Long paths and non-ASCII are in the fixture suite.

**Drydock's own reads and writes in a worktree go through `internal/safefs` (audit 2026-10-16, H1).** The worktree is the agent's to write, and a repository can commit `CLAUDE.md`, `AGENTS.md` or `.claude/rules` as a symbolic link to somewhere else on the machine (the user's credentials file, the app's database). The files Drydock itself reads from a worktree (instruction files for the system prompt and for the generated `AGENTS.md`, manifests for the library versions) and the files it writes there (the generated instruction files and rule files) are opened with `os.Root`: a path that leaves the worktree through `..`, a symbolic link or a junction is an error, a link that stays inside is followed on a read, and a write replaces a link with a file instead of writing through it. Imported repository instruction text is capped at 64 KiB per file and said once, each imported section opens with a line that says it is the repository's own file, that Drydock did not write it and that it is not permission to skip a check, an approval or the task's scope (L17), and the memory proposal made from a person's edit of a generated file is redacted before it is stored, cut to what a person can read whole (`memory.MaxBodyChars`) and offered once for the same text, so the file seen at every task start does not come back as a new proposal each time. Needs a symlink-capable checkout to matter (Developer Mode or WSL on Windows); proven by `internal/safefs/safefs_test.go`, `internal/agents/claude/project_memory_test.go` and `internal/context/context_test.go`.

## 7. Command analysis

`mvdan.cc/sh/v3` v3.14.1 is a POSIX shell parser (it parsed `rm -rf` and `git push --force` pipelines correctly on Linux; go-platform §10) and does **not** parse cmd or PowerShell (phase0 s3.12). On Windows, Claude Code uses Git Bash when Git for Windows is installed and a PowerShell tool otherwise (agent-clis §1); Goose's developer extension depends on Git Bash (agent-clis §13). So three flavors occur and the analyzer must be explicit about what it can and cannot know.

```go
type Confidence int // ParsedExact > LexedConservative > Opaque
type Analyzer interface{ Analyze(ctx context.Context, in CommandInput) (CommandReport, error) }
type CommandInput struct{ Raw string; Shell ShellKind /*bash|powershell|cmd|unknown*/; Cwd string; Root WorktreeRoot }
type CommandReport struct {
    Confidence Confidence
    Invocations []Invocation // program (normalized), argv, redirects, pipeline/conditional edges, nested scripts
    Classes []Class          // readonly, workspace_write, destructive, network, exec_code, deploy, secrets, db_migration, git_history_rewrite, unknown
    Paths []PathRef          // from the path guard
    Kinds []string; HardDeny []string; RuleIDs []string // rule-implied approval kinds, hard-deny reasons, matched rules
    Reasons []string
    Digest string            // goes into ActionDescriptor.ArgvDigest
}
// Decide(report) -> CommandDecision{Verdict allow|ask|deny, Kind, Kinds, Remember, Log}; Policy adds stored rules and CEL restrictions.
```

Pipeline: (1) shell flavor from the adapter (tool name such as Bash vs PowerShell; ACP `execute` kind plus adapter hint); unknown flavor: try POSIX, and if it does not parse cleanly, `Opaque`. (2) Cap input (16 KiB, **design assumption**); longer is `Opaque`. (3) Flavor-specific parse. (4) Normalize the program: strip directory and `.exe/.cmd/.bat/.ps1`, case-fold, apply the alias table (PowerShell `rm, ri, del, erase, rd, rmdir -> Remove-Item`; `iex -> Invoke-Expression`; `iwr, curl, wget -> Invoke-WebRequest` when invoked in PowerShell; `saps -> Start-Process`). (5) Unwrap known wrappers up to depth 3 (`env`, `command`, `nohup`, `time`, `xargs`, `cmd /c`, `powershell/pwsh -Command`, `bash -c`, `wsl -e`, `npx`, `npm run`); beyond that or for unknown wrappers: `Opaque`. (6) Classify against data tables in `internal/security/rules/*.yaml` (reviewable, versioned, testable): destructive (`rm -rf`, `Remove-Item -Recurse -Force`, `del /s /q`, `rd /s /q`, `git clean -fdx`, `git reset --hard`, `git push --force`/`-f`/`+ref`, `git branch -D`, `format`, `diskpart`, `reg delete`), network, deploy, secrets, migrations. These examples are illustrative, not an evidence-backed complete list. (7) Resolve every path-like argument and redirect target through the path guard. (8) Combine: severity is the max, confidence is the min.

Decision table:

| Confidence | Class | Action |
|---|---|---|
| ParsedExact | readonly; or workspace_write with all paths inside the worktree | Allow if CLI mode permits; stored allow rules may apply |
| ParsedExact | destructive, history rewrite, deploy, secrets, migration | `shell_destructive` / specific kind approval; hard-deny set below |
| LexedConservative | readonly or workspace_write inside root | Ask unless a stored rule matches the normalized form exactly |
| LexedConservative or ParsedExact | any path outside root | `fs_outside_worktree` |
| Opaque | any | `shell_unanalyzable`, never auto-allowed |

Implemented defaults where the table above is silent: ParsedExact `exec_code` is allowed and logged; `network`, unknown programs and every ordinary LexedConservative command ask with kind `shell_command` (stored rules may allow them); PowerShell and cmd never exceed LexedConservative until phase B; an unknown shell flavor is parsed as POSIX and capped at LexedConservative when PowerShell or cmd rules match.

Hard-deny set (not approvable from an agent process): production deploy commands (D6), `Set-ExecutionPolicy`, `-EncodedCommand`/`-enc` with non-literal payload, disabling Defender or firewall, `format`/`diskpart`, reading known CLI credential files. A human can still perform the action themselves outside the agent.

**POSIX (Git Bash, WSL).** `mvdan/sh` AST walk collects `CallExpr`, redirects, `Subshell`, `CmdSubst`, `ProcSubst`, `Block`, `IfClause/ForClause/WhileClause`, `FuncDecl`. Command name that is not a literal word (variable, substitution, `eval`, `source`, `.`) is `Opaque`. Parameter expansions in arguments are resolved only when the variable is assigned a literal earlier in the same script; else the argument is marked `dynamic` and path checks treat it as outside the root. Parse error: `Opaque`. **A WSL agent (built, P41):** a Claude Code worker running inside a distro has a Linux shell, so its command is read as bash whatever its tool is called (`CommandInput.WSL`), the worktree root and working folder are taken in their Linux form, every path is checked in the distro's terms and reported at its real Windows location (s6, `Guard.ResolveWSL`), and a Windows path an interop program (`cmd.exe /c type C:\...`) uses is mapped into the distro before the check. Proven by `TestAnalyzerReadsAWSLAgentsCommandsAsBashWithTheDistrosPaths`.

**PowerShell, phase A (v1, ships first).** There is no PowerShell parser in Go and none was evaluated in Phase 0 (**unverified**). Phase A is a conservative lexer written in Go that recognizes a small subset: single and double quoted strings (expandable strings containing `$(`, `${`, or backtick escapes mark the argument `dynamic`), here-strings, statement separators (`;`, newline, `|`, and `&&`/`||` on PowerShell 7), script blocks `{ ... }` analyzed recursively, comments, and simple `Verb-Noun -Param value` invocations. It returns `LexedConservative` only for statements wholly inside that subset; anything else returns `Opaque`: `Invoke-Expression`/`iex`, call operator `&` or dot-source `.` with a non-literal target, `$(...)`/`@(...)` in command position, `-EncodedCommand`, backtick continuation, `[Type]::Method(...)` static calls (except an allowlist such as `[IO.Path]::Combine`), `Add-Type`, `New-Object -ComObject`, `Start-Process`, `Invoke-Command`, `Start-Job`, any pipe into an unknown cmdlet, splatting, and unrecognized parameter binding. Because PowerShell allows unambiguous parameter abbreviation and aliases, the cmdlet table lists aliases and the lexer rejects abbreviated parameters on destructive cmdlets (`-Rec` -> treated as Recurse by treating any unrecognized prefix as `Opaque`).

**PowerShell, phase B (after a Windows proof).** Use PowerShell's own parser out of process: `System.Management.Automation.Language.Parser.ParseInput` returns an AST and parse errors without executing the text. A single long-lived helper (`powershell.exe -NoProfile -NonInteractive`, inside the app's Job Object) receives the command over stdin and returns AST JSON that the same rule engine consumes. This promotes statements to `ParsedExact` where the AST has only literal command elements. Open items (**unverified**, to be measured on Windows): startup and per-call latency, behavior differences between Windows PowerShell 5.1 and PowerShell 7, and whether the helper can be locked down. Phase A remains the fallback when the helper is unavailable.

**cmd.exe.** Lexer for `&`, `&&`, `||`, `|`, grouping parentheses, `^` escapes, quotes, redirections. `%VAR%` and `!VAR!` expansions, `for /f`, `call :label`, and any `.bat/.cmd` invocation (content can change after analysis) make the statement `Opaque`. Destructive table: `del /s`, `rd /s`, `rmdir /s`, `erase`, `format`, `diskpart`, `reg delete`, `takeown`, `icacls` changes.

**Interpreters and package managers.** `node -e`, `python -c`, `npm run`, `npx`, `pnpm dlx`, `uvx`, build tools and test runners execute arbitrary code that no command analysis can see into. They classify as `exec_code`. Inside `check` nodes (human-configured commands) they are expected and allowed. As agent-composed commands they are allowed only when the CLI's own mode permits and are logged; the honest statement is that command analysis reduces accidents and obvious abuse and is not a security boundary against a hostile agent (s3).

Stored policy interplay: CEL rules (google `cel-go`) may restrict which classes/kinds are auto-approved per project, but cannot lower an invariant (hard-deny, opaque never auto-allowed).

## 8. Secrets

Rules (brief §16): never put secrets in SQLite, logs, prompts, events or memory. Provider keys live in Windows Credential Manager via `zalando/go-keyring`; values over 2560 bytes are encrypted in SQLite with the key held in the credential store (the limit is confirmed in source and Microsoft docs, go-platform §3). Missing/locked store is a startup error shown honestly, never a plaintext fallback.

Scanning uses the gitleaks library (`github.com/zricethezav/gitleaks/v8` v8.30.1; `NewDetectorDefaultConfig` loaded 222 rules and flagged a fake AWS key, go-platform §10):

| Scan point | Direction | On finding |
|---|---|---|
| Context Engine package, before sending to any agent or provider | outbound | Redact `[REDACTED:<rule>]` for included snippets; block the source if redaction would change meaning (config files); record in manifest |
| LLMClient request body | outbound | Block call, event `security.secret_blocked` |
| MCP Gateway results | inbound | Redact before the agent sees it; mark untrusted |
| Agent output, tool output, the run's files, room messages, handoffs | inbound | Redact before persistence in SQLite, the room, events and the files under `runs/` (the list below says where each is enforced) |
| Skills and Expert Pack content on import | inbound | Reject or quarantine (brief §9) |
| Memory writes | inbound | Block |
| `secrets` check node (gitleaks) on the repository | worktree | Result posted by the Secrets tool member; also a pre-commit hook in the Taskfile (P5) |

Log and event pipeline additionally uses an exact-value redactor seeded with every secret currently in the credential store (cheap, catches keys that no rule matches), so the structured logger never needs to run regex rule sets per line. Gitleaks throughput under Defender on Windows is **unverified**; scanning is size-capped and runs off the UI path.

**What is scanned before it is stored (built, `internal/redact`, audit 2026-10-16, H7).** The table above was the rule; this is where it is enforced. Every function takes the scanner's `Redact` (gitleaks' rules plus the exact values of the keys the app holds), and JSON is redacted string by string, never as raw text, because a secret can sit across an escape (a private key's newlines are `\n` in the text).

| What | Where | How |
|---|---|---|
| An agent's streamed output and its stderr | `agents/runtime` (`Managed.stream`) | text goes through `redact.Stream`, which holds an unfinished word back until it is whole (a token has no space in it, so it is never split between two stored records); a tool result or other whole chunk is redacted as JSON; the pieces still held are flushed when the run ends |
| The run's chunk files, node outputs and errors, checkpoint state, run result and failure reason | `workflow` (`Config.Redact`, `store.stateJSON`) | scanned before the write transaction opens, so a scan of a large state does not hold the database's one writer |
| Every line a check prints | `checks.Redact` | before the log file, the result's output and the line callback; failing test names are parsed from the cleaned text |
| Room messages | `room.Post` | the body first, then the payload built from it (a decision's text and a task's title are copied from the body), then every string of the payload; a body the scanner cannot read blocks the message, a payload string it cannot read is replaced by `[REDACTED:unscannable]` |
| Review feedback, the reason a task is blocked, evidence summary and data | `tasks.Service.Redact` | before the row is written |
| Events of the families that carry what a tool or a remote service printed (`agent.`, `workflow.`, `check.`, `task.`, `mcp.`, `github.`, `pipeline.`, `watchdog.`, `lead.`) | `events.SQLBus.SetRedactor` (`core.eventRedactor`) | before the event is stored, replayed or delivered; Drydock's own facts (ids, counts, states) are not scanned |

Limits, stated plainly. A word is held back only until the next space, tab or line break, or 4096 bytes: a token is whole inside it, but a run of more than 4096 characters without whitespace is cut at that length and a secret across the cut is not seen. A multi-line secret (a private key's body) whose lines arrive in separate writes is scanned a piece at a time, so the scanner's multi-line rules may not match it. The scanner withholds any input over its size cap (8 MiB) whole (`[REDACTED:oversize]`) rather than store it unscanned. Nothing scans, after the fact, the files an agent CLI keeps in its own folders (Claude Code's session transcripts are its own, not Drydock's to rewrite).

Limits stated plainly: Drydock cannot scan what a CLI reads directly from the worktree and sends to its own provider (a premium CLI sees the files); that is why route choice (s9) and approvals, not scanning, are the control for CLI-originated traffic. The Context Engine excludes by default `.env*`, `*.pem`, `*.pfx`, `id_rsa*`, credential files and anything gitleaks flags from relevant-files selection.

Agent environment (built): agents start from an allowlist (`proc.BaseEnvNames`: PATH, system roots, locale, `HOME`/`USERPROFILE`, proxies and their certificate authorities) plus the names the person chose to pass (settings). Claude Code also keeps `CLAUDE_*` and `ANTHROPIC_*`, which is how the person's own sign-in or API key reaches it (D1: Drydock never reads them); ACP agents keep what their manifest declares. `GH_TOKEN`, `GITHUB_TOKEN`, `CLOUDFLARE_*`, cloud and registry tokens never reach an agent. Project commands (built, `checks.commandEnv`): the `verify`, `red`, `green` and `e2e` checks, the preview command and the dependency scan run code an agent may have just written, so they start from the same allowlist plus the toolchain variables (`proc.ToolEnvNames`: Go, Node, Python, Java, Rust, .NET, the Windows SDK; none carries a credential) and the person's names; a test that prints `GH_TOKEN` prints nothing (`TestACheckDoesNotSeeTheAppsTokens`). A proxy address in `HTTP_PROXY`, `HTTPS_PROXY` or `ALL_PROXY` reaches an agent's CLI and a project command without the user name and password in it (`proc.WithoutProxyCredentials`, audit 2026-10-16 L8), unless the person passes that variable on by name in the settings, which hands it over as it is. A scrub that keeps nothing is an empty environment, never nil (a nil `proc.Spec.Env` means "inherit everything"). Git calls drop inherited `GIT_*` variables (s3); a git call that stays on this machine (everything but push, fetch, pull, clone, ls-remote, submodule and lfs) also gets the allowlist of project commands instead of the app's whole environment, so whatever a configuration could still start there finds none of the tokens the app was started with, while a call that talks to a remote keeps the environment, because the credential helper, ssh and askpass programs read the person's login from it (L8). **Every child process gets `NoDefaultCurrentDirectoryInExePath=1` (built, `proc.WithSafeExeSearch`, audit 2026-10-16, H2):** an agent's working directory is its worktree, and the npm launchers of agent CLIs on Windows (`claude.cmd` and the like) are batch files that run a bare `node`; without the setting cmd.exe looks in the current directory before PATH and runs a `node.cmd` or `node.exe` the agent (or a cloned repository) left there, outside every approval and the sandbox. `proc.Start` always sets it (a caller cannot turn it off), `wsl.BaseEnv` and the git environment carry it, `proc.HardenProcess` sets it in the app's own environment first thing in `main` for everything else it starts (gh, the container engine, npm), and Go's own program lookup then skips the current directory too. Proven on Windows CI by `TestABareCommandInTheWorkingDirectoryIsNotRun` (a `node.cmd` in the working directory runs under a plain cmd.exe and not under `proc.Start`). **WSL agents (built, P41):** wsl.exe copies into the distro only the variables `WSLENV` names, and Drydock sets `WSLENV` itself (any inherited one is replaced): Claude Code's `CLAUDE_*` and `ANTHROPIC_*` (without the Windows-only `CLAUDE_CONFIG_DIR`, which would point the distro's CLI at the Windows sign-in), the proxy and certificate variables (paths with `/p`), Drydock's per-run variables and the person's names. The distro's own `HOME` and `PATH` (a login shell's, from the probe) are set on the command line, never the Windows ones; no value that could be a secret is ever on wsl.exe's command line, which every process can read (`TestAWSLSessionRunsInTheDistroStreamsAndStopKillsItsLinuxProcesses` checks the argv for the key and the gateway token). The gateway token reaches the Windows shim the distro starts the same way: the MCP config the CLI reads names the shim's variables in its own `WSLENV`. OTLP export is off by default and never carries prompts, code, tool output or secrets (brief §10).

## 9. `data_class` enforcement

Definitions: provider `data_class` is `private` or `trainable` (D13 maps the provider report's `public` to `trainable`). Content class is `private` (repo content, diffs, room history, project memory, requirements, private-derived pack content, tool output from private sources; the default for anything not explicitly tagged) or `public_docs` (public documentation text and a CONSULT question that passed the guard below). A `trainable` provider is usable only for Expert Pack CONSULT over public documentation (brief §6).

| # | Enforcement point | Mechanism |
|---|---|---|
| E1 | Router candidate filter | Drop `trainable` candidates when the run's context ceiling is `private`; tier `free` never for agent work. Invariant in code, not a user CEL rule (model-routing s7) |
| E2 | Context Engine | Every manifest entry carries a sensitivity label; `Assemble(target Provider)` fails with `ErrDataClass` if any `private` entry would reach a `trainable` target; the manifest records the refusal (brief §9) |
| E3 | LLMClient | Per-request `DataClass`; wrapper compares with the provider's class before the quota reservation and refuses (brief §8); cache key includes data class |
| E4 | Provider-config writer (OpenCode/Goose/Codex configs) | Writes only providers whose class matches the run; Codex additionally requires validated Responses support (D3) |
| E5 | OpenRouter request builder | Every `private` route sends `provider:{data_collection:"deny", zdr:true}` and fails closed on 404/503 "no endpoint" (D4; model-providers §A.8); never sends `X-OpenRouter-Cache` for private (response cache stores completions at OpenRouter, model-providers §A.8) |
| E6 | CONSULT guard | Query text is built from the user's question plus pack metadata, scanned by gitleaks, and rejected if it contains winnowed shingles matching repository file content (**design assumption**, threshold to be tuned) or exceeds a length cap |
| E7 | MCP Gateway | A run whose provider is `trainable` has no repo-reading tools at all; results from private sources are never forwarded into CONSULT |

Provider presets (evidence in model-providers §A-E): OpenRouter paid with the request filter `private`; OpenRouter `:free` and `openrouter/free` `trainable`; OpenRouter paid without the filter `trainable`; Anthropic API and OpenAI API `private` (OpenAI evidence is secondary and must be re-verified against the live data-controls page); Google AI Studio from an unbilled project `trainable`, from a user-attested billing-enabled project `private` only with grounding, Interactions `store`, File API and explicit caching disabled; self-hosted vLLM/SGLang/Ollama `private` on loopback or behind verified TLS plus auth. Anthropic Covered Models require 30-day retention and are not available with ZDR; a policy demanding zero retention excludes them and the 400 retention error maps to a clear message (model-providers §D). Subscription CLI routes (Claude Code, Codex, Antigravity, Gemini CLI) have vendor-side retention and training terms that depend on account settings Drydock cannot read; the appendices do not establish them (Q2). A Gemini API key from an unbilled project is `trainable`, so a Gemini CLI/Antigravity agent on such a key cannot work on private code.

Transport rule (brief §16): hosts without TLS only on loopback or private addresses; public hosts require verified HTTPS (self-signed pinned by SHA-256 fingerprint). Enforced at registration and at dial time (custom `DialContext` rechecks the resolved IP to resist DNS rebinding; **design assumption**). Tension: a bare Ollama has no inbound auth or TLS (model-providers §E, source grep), so a LAN Ollama is not safely `private`; a non-loopback plain-HTTP host requires an explicit user attestation and a warning, and defaults to concurrency 1 (Q3).

## 10. Untrusted content

Untrusted sources: repository files and comments (including AI-written ones), dependency code, Expert Pack and doc content (Cloudflare, Microsoft Learn, Context7), MCP tool output, GitHub issues/PR bodies/review comments/CI logs, Linear/Notion/Sentry/Aikido items, requirements documents, skills from registries, web pages, other agents' messages, and the output of any tool.

Rules:
1. Context Engine wraps each such entry in a typed provenance block (`<untrusted source="mcp:github" ref="..." fetched="...">`) placed after the stable prefix and never in a system/role/instruction position. Wrapping is a mitigation, not a guarantee.
2. Untrusted content never: creates or answers an approval, edits permissions or tool allowlists, edits CEL rules or routing policy, edits project memory or standing instructions without a human accepting the diff, creates a task or milestone without a human action or a stored rule (brief §11), or selects a provider/model.
3. Content derived from untrusted input that feeds an outbound write (PR comment, issue update, Notion/Linear write) goes through `integration_write`/`mcp_write_tool` approval with the origin shown.
4. The MCP Gateway marks results untrusted, scans them for secrets, shapes/truncates them and writes a per-call audit event (brief §14). Skills are glob-scoped Markdown pinned to commits, scanned for secrets and injection, never pulled from arbitrary GitHub (brief §9).
5. Agent-to-agent messages are untrusted by the recipient. They are delivered with author attribution as quoted data. An agent message can ask a human a question; it can never answer one.
6. Review-comment and issue text from GitHub is untrusted even when authored by the user's collaborators (brief §13b).
7. Injection heuristics (instruction-like phrases, tool-call-shaped text, hidden Unicode) raise a warning label in the UI and add a `suspicious` flag in the manifest. They are never relied on to block.
8. Lethal-trifecta guard (T11): a run that has private data, untrusted content and an egress-capable tool in the same session gets its MCP allowlist narrowed by role and surfaces a warning; where the CLI offers tool-restriction flags the adapter applies them.
9. Because injected output can only cause actions that pass through approvals, the approval dialog shows the canonical action (s5), not agent narration.

A gate blocks adapter startup unless a consent for the current terms version exists; a terms version bump re-prompts. Consent text is shown verbatim and its hash stored.

## 12. Audit log

Append-only table `audit_log(seq, ts, actor, action, subject, detail JSON, prev_hash, hash)` (approval id, action hash, outcome and rule ids travel in `detail`; the scanner redacts `detail` before it is stored; `UPDATE`/`DELETE` are refused by triggers as defense in depth); `hash = SHA-256(prev_hash || canonicalJSON(row without hash))`. Written in the same SQLite transaction as the effect it records (single writer connection, phase0 s3.13). `Verify` detects edits, deletions and reordering; truncating the tail is detected only against a previously recorded head hash. Records: approval request/decide/consume/mismatch, path-guard denials, analyzer verdicts with `Digest`, consent events, provider data_class refusals, secret findings (rule id and location only, never the secret), Gateway calls, hard-deny hits, credential-store access, permission-mode changes, repo-config drift. It is a security view over the append-only event bus (`approval.*`, `mcp.*`, `watchdog.*`...), retained indefinitely like events (brief §18). The hash chain detects accidental or agent-made edits; it does not stop a same-user process from rewriting the whole file (T9). An "export audit log" action writes an unsigned JSON bundle for the user.

## 13. Cloudflare preview/production separation (D6)

Cloudflare is an agent-side template, not part of Drydock's infrastructure. No token scope separates preview from production: upload-version, create-deployment and direct upload all need `Workers Scripts Write`; Pages uses `Pages Write` for both and `--branch` decides which (tooling §1d). `wrangler versions upload` Version URLs reuse the Worker's existing configuration and resources (production bindings); `wrangler preview` (Wrangler >= 4.135, `previews` block required) isolates Durable Objects and, with separate bound resources, KV/D1/R2, while service bindings, routes, cron and queue consumers still point at production (tooling §1c).

Controls:
1. Preview credentials belong to a **separate Cloudflare account** (or none). An account-scoped token cannot touch another account: the only real boundary.
2. Production tokens never enter agent processes (env builder, s8). Verified by an integration test that dumps the agent environment.
3. Agent-process command allowlist enforced by the analyzer plus PATH shims (`wrangler.cmd` shim first on PATH in the agent environment, delegating after checking argv): allowed `wrangler dev` (ports allocated by Drydock: `--port`, `--inspector-port`), `wrangler preview ...`, local D1 migrations with `--persist-to`, `wrangler types`, `wrangler d1 ... --local`; allowed only when the preview credential is a separate account: `wrangler versions upload`; denied: `deploy`, `pages deploy` (`--branch` can equal the production branch), `rollback`, `delete`, `secret put/delete` (non-preview), `d1 ... --remote`, `kv`/`r2` writes against non-preview resources, and any `cf deploy` equivalent. The allowlist also covers the new `cf` CLI (beta) names (tooling §1c).
4. Starter template `previews` block binds separate KV/D1/R2/DO resources; the `preview` check (brief §13a) uses the preview-account credential and posts the URL through the Preview tool member. Production deployment is never a check.
5. PATH shims and analyzer are cooperative: `npx wrangler`, absolute paths into `node_modules\.bin`, or a script run via `node` can bypass them. The real protection is credential absence. Where Wrangler caches an OAuth login (`wrangler login`) and whether it can be redirected per agent (for example a per-agent config home) is **unverified** (Q6). Until proven, onboarding tells the user to keep the production Cloudflare login out of the Windows profile that agents run under.
6. `wrangler dev` state is `<worktree>\.wrangler\state` per worktree; migrations are applied per worktree; workerd file locks when deleting worktrees are unverified (tooling §1e, §8).

## 16. The repository's own supply chain (audit 2026-10-16, M19, L49 to L52, L54 to L57)

The repository is public, and a pull request from anyone's fork runs its workflows, so the automation is held to what a stranger's
code could reach.

- **Runners and tokens.** Every job of `ci`, `verify`, `windows-probes`, `contract` and `security` says `runs-on: windows-latest`
  or `ubuntu-latest` outright, so no repository variable can send fork code to a self-hosted runner on a person's PC; every
  workflow has a `permissions:` block that is read-only, every job a `timeout-minutes`, every checkout `persist-credentials: false`.
  `internal/ciconfig` reads the workflows and fails if one of these stops being true, and if a multi-command PowerShell step could
  hide a failed command (`$PSNativeCommandUseErrorActionPreference`, L49).
- **Secrets.** The sign-in secrets of the contract suite belong to the GitHub environment `contract`, which only `main` may use, and
  only its suite step holds them. The newest agent CLIs are installed by a step of their own that holds none (npm runs with a scrubbed
  environment, and Claude Code's npm package needs its install script, so what keeps the secrets safe is that the step has none).
  `internal/security` runs the secret scan the product uses (gitleaks' rules) over every tracked file that is not a test, a fixture
  or a lock file, with every `go test`, and `.gitignore` keeps env files, databases, keys and Playwright results out (and a test
  fails if a tracked file is one it ignores).
- **Known vulnerabilities and code scanning.** `security.yml` runs weekly, by hand and when a dependency file changes: `govulncheck`
  at a pinned release (fails if the code can reach a known vulnerability), `npm audit` against the lock file (high or worse), and
  CodeQL for Go and JavaScript/TypeScript. It is not part of the merge gate (a new advisory against an unchanged dependency must not
  stop an unrelated change): the weekly run is read. CodeQL runs with two queries switched off, each with its reason, in
  `.github/codeql/codeql-config.yml` (a path filter does not work for Go): `go/disabled-certificate-check` (the one
  `InsecureSkipVerify` in the product pins a provider's certificate by its SHA-256 in `internal/providers/pinned_tls.go`; the query
  cannot see the check that replaces the chain check) and `go/unvalidated-url-redirection` (the product issues no redirect; the two
  in the Go code are in the stand-ins for authorization servers that the tests talk to, which redirect to the `redirect_uri` they are
  sent, as the protocol has it). `internal/ciconfig` fails if a third query is switched off, or if any other non-test Go file names
  `InsecureSkipVerify` or issues a redirect. Dependabot proposes updates with a 14-day cooldown. `SECURITY.md` says how to report a vulnerability
  privately.
- **Code an agent wrote, run by the harness.** The trial's acceptance runs it with `proc.ToolEnv` (no token) and accepts only if every
  hidden test was seen to pass (`docs/evals.md` section 13). Recorded runs are committed with the account's plugin and connector
  details and the machine's paths removed.
- **Not done here.** Pinning `Vampire/setup-wsl` (the only third-party action) to a commit needs its repository, which this work could
  not read; it stays on its major tag. The GitHub environment, its branch rule, the move of the two secrets and private vulnerability
  reporting are settings only the owner can make (`docs/contract-tests.md`).
